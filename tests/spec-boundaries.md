# Этап 2: граничные сценарии Git

Источник: `docs/SPEC.md`, разделы «Git-логика» и «Этап 2».
Сценарии: `tests/cases/git-boundaries.ts`, общие для двух раннеров с проверками через `node:assert/strict`.
S2-B01…B12 — исходные 14 сценариев (B04 в трёх вариантах); S2-B13…B33 — этап 0B.
В исходных сценариях изменены только вызовы под порт 0B: worktree создаётся через `createWorkspace`; для B04/B06/B07 кандидат готовится до порчи состояния основной копии, затем `applyWorkspace` отклоняется; конфликт B12 возникает в `prepareWorkspace`. Assertions сохранены и дополнены проверкой полного состояния (индекс, refs, незавершённые операции).
Вход Vitest: `tests/spec-boundaries.test.ts`; команда после настройки общего раннера: `npm test -- tests/spec-boundaries.test.ts`.
Запуск без зависимостей на Node 24: `node --test tests/run-git-boundaries.node.ts`.

Каждый тест создаёт настоящий временный репозиторий внутри `.tmp/`, затем удаляет свой каталог.
Удалённый репозиторий в push-тестах — локальный bare-репозиторий; сетевые сервисы не нужны.
Репозитории с пробелами в путях используются во всех сценариях.

## Контракт и границы проверки

Тесты проверяют производственный порт `src/core/ports/git.ts` (запросы, результаты, `GitError`/`GitErrorCode`, `GitOperationStore`, `GitFaultPoint`); дубль контракта удалён, `tests/contracts/git-boundaries.ts` лишь реэкспортирует типы порта.
Спецификация не фиксирует имена методов; они согласованы командой 0B и зафиксированы в порте.
`createGitAdapter({ store, faultInjector })` экспортируется из `src/adapters/git/index.ts`.
UI-предупреждения, выбор другой цели и подтверждение `git init` здесь не проверяются: проверяется результат адаптера для будущего UI.
LFS проверяется по атрибутам, без скачивания LFS-объектов и установки расширения.

### Что доказывают сценарии 0B и чего не доказывают

- Тестовый `GitOperationStore` — память процесса теста. Он проверяет протокол фаз, идемпотентность и сверку по фактическому Git, но **не** доказывает восстановление после реального падения приложения: исключение из `faultInjector` имитирует смерть процесса только на границах фаз, а не посреди системного вызова Git. Durable-хранилище (SQLite) и его приёмка — этап 1.
- Проверяются фактические HEAD, дерево индекса, содержимое файлов, `refs/vibestudio/*` и следы незавершённых операций (`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-*`, `SQUASH_MSG`), а не только код ответа.
- Блокировка внутри приложения (S2-B22) не защищает от внешнего Git и редактора: окно между проверкой и записью закрывается лишь отказом Git при расхождении базы/перекрывающей правке (S2-B29–B31).
- Эксперименты по порядку шагов (предыдущая сессия B, временные репозитории): заранее созданный squash-коммит (`commit-tree`, родитель = ожидаемая база) + `merge --ff-only` обновляет индекс, файлы и ref одним шагом Git, но не атомарно; раздельный вариант `read-tree -m -u` затем CAS `update-ref` оставляет безопасное окно «HEAD = база, индекс = кандидат, файлы = индексу»; порядок «ref, затем файлы» оставляет обратный staged-diff и отвергнут.

### Отложенные задачи G8–G10 (не входят в 0B, оформлены для следующих итераций)

| ID | Задача | Обязательные проверки |
|---|---|---|
| G8 | Push только в выбранный настроенный remote | Имя вне `git remote` отклоняется; URL/путь вместо имени отклоняется; проверяется фактический push URL и транспорт (допустим локальный bare для тестов; `ext::`/произвольные helpers отключены); цель и ветка передаются для подтверждения, смена URL требует нового подтверждения; таймаут → проверка удалённого ref до повтора; S2-B08/B09 сохраняются |
| G9 | Таймауты, hooks/signing, preflight автора | Отдельные таймауты для чтения, merge/apply и push; политика hooks/signing задокументирована, обязательное подписание, которое приложение не выполнит, даёт отказ; author/committer проверяется до изменения основной копии (часть уже в S2-B26) |
| G10 | Откат частичного `createWorkspace` | Сбой после `worktree add` (запись config, ветка, base-ref) удаляет только доказанно созданные операцией ресурсы; при сбое компенсации сохраняется исходная ошибка и остаётся восстанавливаемая запись; пользовательские данные в новом worktree не удаляются |
