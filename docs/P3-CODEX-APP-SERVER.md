# P3: Codex через app-server

Редакция 2026-10-27. Этот документ описывает отдельный транспорт `codex-app-server-read-v1`. История исследований `exec`, R2/R3 и их исходные результаты сохраняется в прежних документах и fixtures.

## Реализация

`createCodexAppServerAdapter` экспортируется из `src/adapters/codex/index.ts` и реализует общий `AgentAdapter`. Его запрос явно выбирает новый профиль. Старые фабрика, профили и отказ `exec resume` сохраняются; автоматической смены прав нет. Подключение адаптеров к durable SessionEngine/UI относится к P5 и не входит в P3.

На каждый ход запускается отдельный `codex app-server --listen stdio:// --strict-config`. Перед ним выполняются три конечные диагностики: версия, help app-server и штатный login status. Поддержанная версия — **0.163.0, macOS arm64**. Авторизация, HOME и CODEX_HOME наследуются; credentials не копируются, глобальная конфигурация не изменяется. Новый двусторонний ProcessRunner сохраняет ограниченные очереди, учёт выхода/EOF, остановку собственной группы и полный список ошибок завершения. Исходный runner Claude/R2 не изменён.

Порядок RPC: `initialize` → `initialized` → `config/read` → `thread/start` либо `thread/resume` → `thread/inject_items` → `turn/start`. Входящий поток проверяется по ID запросов, thread и turn; неожиданный server request, повреждённый JSON/UTF-8, инструмент вне профиля, переполнение или timeout завершают ход ошибкой. Stop использует `turn/interrupt` и конечное принудительное завершение при отсутствии ответа. Итоговый `run_finished` единственный и согласован с `done`; ошибки остановки не скрываются значением interrupted.

`thread/resume.developerInstructions` сам по себе не обновляет сообщение в модельной истории установленной CLI. `collaborationMode.settings.developer_instructions` также не решает задачу: каталог модели может подставить собственный текст. Рабочий маршрут использует документированный `thread/inject_items` и `features.retain_client_developer_messages=true`. Он добавляет текущий `buildAgentInstructions({resume})` как собственное developer-сообщение приложения перед каждым ходом. Старые сообщения/файлы истории не переписываются; пользовательский prompt остаётся пользовательским. API не принимает произвольную историю, путь transcript или injected items из UI. Resume допускается только для собственного UUID с привязкой session/participant/workspace/cwd/transport/profile; при новом экземпляре адаптера привязку подтверждает доверенная композиция.

Основание: [официальный протокол app-server](https://learn.chatgpt.com/docs/app-server), [тесты developer injection закреплённого исходника](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/tests/suite/v2/thread_inject_items.rs), [сохранение injected items без нового модельного хода](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/session/inject.rs). Experimental API привязан к проверенной версии; это не обещание совместимости следующего релиза.

## Профиль чтения

Сохранены пять требований выбранного пользователем варианта с shell: `shell_sandboxed`, `reads_scoped`, `writes_forbidden`, `project_extensions_disabled`, `user_extensions_disabled`. Профиль `vibestudio-read-v1` задаёт root deny, minimal read, единственный workspace read, network disabled и approval never. Он передаётся при first, resume и turn/start; ответ thread проверяется до модельного запроса.

У app-server отсутствуют прежние ignore-флаги. Вместо молчаливого наследования настроек используется отдельный проверяемый механизм:

- Проектные конфигурации исключаются явным untrusted для cwd и предков; доверие проекта со стороны приложения не включает расширения CLI.
- Hooks, apps/plugins, cloud/bundled skills, web, изображения, goals, делегирование и подстановка collaboration/app instructions выключаются явными overrides. Метаданные доступных skills перечисляются и каждый путь отключается; локальные AGENTS/rules, неоднозначные пути и symlinks дают отказ до CLI.
- `config/read` проверяет эффективные обязательные поля и отсутствие известных подмен инструкции, каталога модели, провайдера и shell env. Все реально загруженные имена MCP выключаются объектом в thread config **до создания thread/подключений**. Ответ config/read может содержать секреты и не журналируется.
- Изменение executable или метаданных расширений между подготовкой и стартом даёт отказ. Конфликт обязательной политики не превращается в неизвестное положительное наблюдение.

Граница доверия остаётся прежней: `cli_configuration_not_audited`, `os_isolation_not_attested`, `network_not_restricted`, `detached_children_not_guaranteed`. Приложение не аттестует всю CLI/managed-политику, штатные auth/helpers и сеть провайдера, все файлы класса `:minimal` или отделившихся потомков. Shell позволяет команды чтения внутри профиля, а не только закрытый список Read/Glob/Grep. Обычное чтение моделью файла `SKILL.md` по явному запросу возможно; оно отличается от автоматического подключения навыка расширением CLI.

## Живая приёмка

Точка входа — `tests/live/codex-app-server.probe.ts`; обычный CI её не запускает. Пользователь поручил текущему одиночному Codex завершить P3, разрешил полный доступ и затем реализацию. Повторное согласие на команды этого объёма не запрашивалось. Исполнитель работает только в `0712ff57…/session`, проверяемые проекты — собственные одноразовые tmp.

Каждая редакция M ограничена **4 модельными + 12 диагностическими + 3 вспомогательными** запусками, 440 с; каждый ход ≤95 с. Вспомогательные — git init, сборка C-пробы и положительный запуск C-пробы. Однократный latch создаётся с `wx`. Перед каждым spawn сверяются SHA wrapper/native/Node и замкнутого графа TS-исходников. Отказ обязательного критерия останавливает последовательность. Нет synthetic detect/admission или подставленной авторизации.

| Проверка | Критерий |
|---|---|
| M1 | Реальный файл, новый UUID, точный полный первый абзац инструкции, MEMORY только в истории |
| M2 | Новый процесс/экземпляр, тот же UUID, MEMORY без повторения в prompt, точный новый абзац resume |
| M3 | Три неверных ссылки/привязки: invalid_request, ноль процессов |
| M4 | Точный результат cat; положительный контроль и пять C-операций в sandbox; effective policy и фактический runtime inventory; неизменность файлов/отсутствие эффектов hook/MCP |
| M5 | Stop после текста/инструмента, interrupted/stopAccepted, один terminal, подтверждённые exit и EOF |

M4 разбирается независимо от production-нормализации. Из RPC берётся реальный `commandExecution.aggregatedOutput`, а не пересказ модели. Собственная история читается только по UUID наблюдённого M4. Для app-server проверяются **оба** снимка политики: служебный `auto-compact-0` после inject и реальный turn, связанный с RPC. Каждый снимок должен пройти прежнюю строгую проверку; политики должны совпадать. Лишние/отсутствующие/изменённые снимки дают отказ. Runtime inventory берётся из результата собственного вызова `ALL_TOOLS`, связанного по call_id.

Первый набор r01 остановился на M4: все проверки кроме effective policy прошли. Причина — использование старого exec-инспектора, который требует ровно один снимок; настоящий app-server сохранил два одинаковых. Исходный failed сохранён. Отдельный RPC-инспектор проверен на этом же результате и отрицательных мутациях, старый exec-инспектор не ослаблен. Production-код между r01 и r02 не изменялся.

Безопасные проекции evidence содержат результаты, команды собственного стенда, SHA исходников и бинарников. Config/read, пользовательские настройки, credentials, reasoning и входные developer-инструкции в fixtures не экспортируются. Полные исходные журналы остаются приватными материалами собственной проверки.

### Результат и расход

**P3 завершён для `codex-app-server-read-v1`.** r02 дал M1/M2/M3×3/M4/M5 passed; все 16 CLI-запусков имеют exit 0, оба EOF и пустые issues, cleanup=removed. Stop принят после активности и завершил ход как interrupted. Перепроверка сохранённых результатов восстанавливает точные абзацы first/resume и общую память, фактическое чтение и пять C-операций, оба снимка политики и каталог инструментов. Старый `exec resume` не объявляется исправленным. P4 и durable UI/engine не начаты; весь этап 0C этим не закрывается.

Доказательства: [успешный r02](../tests/fixtures/codex/observed-0.163.0-app-server-r02.json), [исходный отказ r01](../tests/fixtures/codex/observed-0.163.0-app-server-r01.json), [ранние исследования](../tests/fixtures/codex/observed-0.163.0-app-server-research.json). Manifest r02 содержит 29 TS-файлов, SHA сериализованного manifest `f3b4c6499599968b16ece340b8142672dd8d982841297d962ed8f299066efb95`. Независимые тесты проверяют этот SHA и текущую идентичность production-файлов.

После M добавлен один отказ допуска: неизвестный явно включённый feature-флаг (например computer_use/js_repl/browser_use) блокируется до thread/start. Транспорт, инструкции, модельные запросы и политика файлов не менялись. Изменённый preflight проверен отрицательными тестами и **отдельным реальным немодельным** `initialize → config/read`, exit 0, cleanup=removed; ни thread, ни turn не создавались. [Evidence усиленного допуска](../tests/fixtures/codex/observed-0.163.0-app-server-config.json) отдельно фиксирует актуальный SHA `app-server-policy.ts`; живой r02 не приписывается этому последующему изменению.

Модельные числа — попытки запуска CLI с ходом модели, не количество оплаченных обращений к провайдеру. Ранние исследования имели собственные одноразовые latches и конечные бюджеты; неудачи не удалялись. Общий расход предыдущего продолжения (13/33/16) остаётся отдельно в прежнем отчёте и не входит в эту таблицу. Повтор M не делался при неизменных условиях: r02 последовал после исправления инспектора и отрицательных регрессий.

Пять C-операций не объявляются доказательством всех инструментов. Дополнительно сохранено предыдущее живое [R4 first/resume](../tests/fixtures/codex/observed-0.163.0-r4-r02.json) того же закреплённого бинарника: запрет apply_patch подтверждён диагностикой CLI. Новый RPC использует тот же core и именованный профиль; M4 независимо сверяет exact effective policy и отсутствие writable roots. Альтернативная запись в новом M не повторялась. Автоматическая загрузка skills проверяется отдельно от чтения SKILL.md обычной shell-командой; такое чтение случилось в r01 по запросу пробы и не скрывается.

Проверки окончательной редакции: **1762/1762 Vitest** (51 файл, `--maxWorkers=2`), затем отдельно **78/78 Node** (7 наборов), без skipped/todo. Electron подтвердил окно и preload. Полный Vitest и Node выполнялись последовательно. SHA успешной fixture r02: `3a476f1be0e11ad03cfd26d7b03de40dfb40779141aec127b093b1d836bddccc`. Проверки не требуют запускать реальную модель в обычном CI.
