Один SessionEngine обслуживает обе CLI. Выбор закреплён за participant вместе с профилем: Claude — `practical-local-v1` с существующим набором чтения; Codex — `codex-app-server-read-v1`. Производственная композиция создаёт существующие Claude/Codex app-server адаптеры через `createSoloAgents`; synthetic agents есть только в тестовых стендах. История перед resume сверяется с CLI, participant и собственным transcript. История другой CLI не подставляется.

`core` использует порты и переданные часы/генератор ID; Node/Electron и SQLite находятся снаружи. Main проверяет источник IPC, главную frame и URL окна, строгую схему, принадлежность сущностей и допустимость переходов. Renderer передаёт ID, prompt и явное решение о новом диалоге; пути, argv/env и разрешающий флаг не принимаются. Preload выставляет только фиксированные методы, уведомление очищается от Electron event. Универсального exec, fs, process и SQLite в renderer нет.

## Рабочий путь в UI

1. «Выбрать проект» открывает системный выбор каталога через main. Проверяется существующий Git-репозиторий с историей и активной веткой. UI показывает доверие выбранному локальному проекту, выбор CLI и создание сессии.
2. Создание сессии сохраняет намерение, создаёт отдельный workspace существующим Git-адаптером и показывает подготовку. Настроенный `scripts.setup` читается из закоммиченного `package.json`, который попадёт в workspace. Само выделение workspace не выполняет setup.
3. При необходимости UI показывает команду, cwd, версию настроек, фактические права файлов/сети, запрос повышенных прав, имена переменных окружения, fingerprint и известные исполняемые входы. Текущий исполнитель setup имеет файловый доступ без песочницы, сеть разрешена, повышение прав не запрашивается. Без отображаемой области подтверждение недоступно. Значения окружения в UI не передаются.
4. Подтверждение передаёт только requestId/sessionId/challengeId и показывается только при разрешённом `actions.prepareSetup`. Завершённый setup нельзя исполнить повторно через новый invalidated challenge после restart; UI объясняет необходимость новой сессии. Отзыв сохранённого согласия доступен и после завершения. После подготовки можно отправить задачу. Return отправляет, Shift+Return добавляет строку; незавершённая IME-композиция не отправляет. Кнопка Stop доступна во время запуска.
5. Ответ задачи и завершение процесса показаны раздельно. Ошибка, прерывание, потерянная история и неопределённый исход различимы текстом и значком. Можно продолжить диалог той же CLI; при потере transcript нужен явный новый диалог с предупреждением о потере контекста.
6. После перезапуска выбранная сессия восстанавливается по ID, а история читается из SQLite. Неопределённый прежний эффект блокирует конфликтующий запуск и объясняет причину; автоматического повторения setup нет.

UI использует существующие токены DESIGN, светлую/тёмную тему, видимый клавиатурный фокус и reduced motion. Основные действия доступны при минимальном окне 640×480 и масштабе 200%; для увеличенного текста предусмотрена прокрутка. React выводит модельный текст как текст, без HTML, внешних ресурсов и автоматического выполнения ссылок. Ни HTML-подобный ответ, ни лог не создают DOM-изображение/скрипт.

Лента подписывается до первого чтения, а уведомления служат подсказкой дочитать SQLite. Страницы по 100 событий читаются по возрастающему seq; потерянное уведомление компенсирует периодическая сверка раз в 2 секунды. Чтение уступает выполнение между страницами; видимая лента хранит последние 300 событий, более ранние доступны страницами. UI предупреждает, что сообщение на границе страницы может быть неполным: snapshot или часть delta могут находиться на соседней странице. Один отображаемый текст ограничен 64 000 символами с явной отметкой; исходные события остаются в БД. Повторные уведомления не создают повторных эффектов. При транспортной ошибке UI предлагает повтор исходного запроса с теми же данными и requestId.

До IPC renderer сохраняет строгие метод и полное тело команды в `sessionStorage`. После reload очередь восстанавливается без автоматического исполнения: пользователь явно повторяет исходное действие с прежним requestId, а новые создание/отправка заблокированы до получения ответа. Stop хранится отдельной записью и не удаляет ожидающий send; ответ удаляет только свою запись. Повреждение записи или отказ хранения не обходятся новым ID и не позволяют отправить непроверенный запрос. Это память запросов одного окна, включая пользовательский prompt, а не второй источник состояния: после закрытия окна восстановление этой очереди не гарантируется. История и уже принятые операции восстанавливаются из SQLite.

## SQLite и операции

Настоящая файловая БД открывается через `better-sqlite3`. Схема — `src/adapters/store/migrations/0001-initial.ts`; миграции нумерованы подряд и входят в сборку как TS-модули. Используются `PRAGMA user_version`, application_id `VSTU`, WAL, `synchronous=FULL`, FK и `busy_timeout=5000`.

Проверенная durable-гарантия относится к падению процесса, в том числе SIGKILL. На macOS здесь используется fsync без F_FULLFSYNC; сохранность при внезапной потере питания этим этапом не доказана.

Таблицы: projects, sessions, workspaces, participants, turns, events, operations, git_operations, consents, workspace_leases. Составные FK связывают session/workspace/participant/operation; requestId уникален, seq событий уникален внутри сессии. Частичный UNIQUE допускает один активный ход participant. Триггеры защищают историю от удаления/перезаписи, закрепление CLI и неопределённый слот от неявного повторного захвата. Удаление физического workspace не удаляет историю.

`beginOperation` одной транзакцией сравнивает fingerprint и сохраняет намерение вместе с исходным изменением. Неизменный повтор возвращает существующую operation; иное содержимое при том же requestId даёт конфликт. `commit` одной синхронной транзакцией записывает состояние и нормализованные события, выдаёт seq и только после COMMIT позволяет уведомить UI. SQLite, Git и процесс не составляют общей транзакции; exactly-once внешнего исполнения не обещается.

Перед обновлением существующей схемы делается согласованная копия `VACUUM INTO` с проверкой целостности и прежней версии. Миграция и изменение user_version проходят в транзакции; при ошибке она откатывается. Более новая или чужая БД проверяется read-only и не переводится в другой режим журнала. Тесты проверяют пустую БД, искусственное обновление, rollback, согласованную копию, более новую/чужую/повреждённую БД и ограничения схемы.

Первая ошибка записи SQLite блокирует последующие записи и новые внешние эффекты. Engine инициирует безопасную остановку активного запуска; прочитанная история не маскируется выдуманным success. Ошибки ограничений и конфликт requestId отличаются от повреждения/отказа записи. Durable GitOperationStore использует то же соединение и защёлку отказа, сохраняя контракт 0B.

JSONL — ограниченная диагностика: по умолчанию до пяти файлов по 1 MiB, с ограничением полей и частичным скрытием распространённых секретов. Это не второй источник бизнес-состояния. Отказ журнала не откатывает зафиксированные SQLite события и не меняет результат задачи. Автоматическое копирование `.env` и общий изменяемый `node_modules` отсутствуют.

## Recovery, Stop и согласие

| Сохранённая граница | Поведение после restart |
|---|---|
| Транзакция намерения не завершилась | Нет операции и её события, внешний эффект не запускался |
| `intent_saved` у хода/setup, исполнитель ещё не мог вызываться | Прерывание без автоматического повтора; слот можно освободить при доказанном отсутствии попытки |
| Незавершённый `create_session`, включая `intent_saved` | Консервативное `recovery_required`; workspace сверяется, второй `createWorkspace` не вызывается. Исключение — доказанная завершённая компенсация из durable Git-записи: чистый отказ без повтора |
| `effect_pending`, `effect_started`, результат ещё не сохранён | Неопределённый исход, `recovery_required`, блокировка слота; нет автоматического повтора или сигналов старому PID |
| Результат и состояние зафиксированы | Восстановление сохранённого результата без повторного запуска |
| Workspace или transcript исчез | История приложения сохраняется; workspace недоступен либо resume запрещён; новый диалог требует явного решения |

Engine сверяет физический workspace и доступность истории. PID не является доказательством принадлежности; по имени процесса или совпадению argv ничего не завершается. Неопределённый слот в P5 нельзя снять общей кнопкой «продолжить»: автоматическая выдача полномочий ради удобства не добавлена.

Для неудачного `create_session` engine дополнительно читает durable-запись GitOperationStore через read-only порт. Только совпавшие requestId и полная identity, сохранённая исходная ошибка, подтверждённый `cleanup=completed/not_needed`, отсутствие ошибки cleanup и фактически отсутствующий workspace дают чистый отказ `workspace_failed`: сессия `error`, слот `released`, без повторного создания. Отсутствующая/чужая запись, оставшийся каталог, неполная компенсация или неизвестный результат сохраняют `recovery_required`. Та же сверка применяется после restart, если Git уже записал компенсацию, а engine ещё не записал результат.

Stop сохраняется как команда с requestId, идемпотентен и ограничен сроком ожидания. Принятый Stop не превращается в успех из-за позднего результата. Перед освобождением слота учитываются исход задачи, подтверждённый выход, EOF, предел ожидания, ошибки сигнала и issues. Поздняя ошибка interrupt тоже учитывается. Неподтверждённый exit или ошибка отправки сигнала удерживают слот. Завершение основного процесса не доказывает завершение отделившихся потомков.

Ошибка самого обработчика Stop фиксирует ошибку этой команды и diagnostic; она не передаёт Stop слот агентной операции, не перезаписывает ход и не блокирует весь engine ложным `lease_busy`. Причины ограничений Store остаются в ограниченной диагностике `store_constraint`; ошибка ограничения не равнозначна отказу SQLite.

P4 не реализован заново: сохранение добавлено к действующей политике и snapshot-адаптеру. Сохраняются область, версия, fingerprint, статус согласия/отзыва/инвалидирования. Challenge не персистится; новый экземпляр имеет новый namespace ID. Сохранённое согласие — кандидат, который требует нового capture. Изменение команды, аргументов, cwd, прав, env, назначения или известных входов инвалидирует прежнее разрешение. Повтор без изменений разрешён только после проверки.

Исполнитель повторно проверяет тот же замороженный `ProjectCommandRequest`, который передаёт ProcessRunner. Неизвестный снимок, изменённые входы и поддельный разрешающий флаг не запускают команду. Остаются документированные пределы P4: неполнота анализа произвольного исполняемого графа и гонка между снимком и spawn. Согласие на setup не разрешает push, публикацию и разрушительные операции.

## Workspace и необходимые G9/G10

Переиспользован существующий Git-адаптер. Для чтения, записи и сети заданы конечные таймауты. Hooks выключены для внутренних команд Git; обязательная подпись, которую адаптер не выполнит, даёт отказ до изменения. Автор проверяется до операций создания коммита. Подробности и изменения двух старых ожиданий объяснены в [границах 0B](../tests/spec-boundaries.md).

Создание workspace сохраняет durable-намерение и признаки созданных ресурсов. Компенсация проверяет владение и состояние ветки/base-ref/worktree, не использует принудительное удаление пользовательских данных, сохраняет исходную ошибку и ошибку cleanup. SIGKILL не изображается как обработанное исключение: неопределённая операция не повторяется автоматически.

Ресурс, появившийся во время команды с неподтверждённым исходом, не присваивается операции только из-за совпадения SHA или регистрации: он сохраняется. Перед удалением подтверждённого worktree проверяются путь, ветка, HEAD и пользовательские файлы, включая ignored. Это отдельная проверка удаления: обычная семантика чистоты 0B не изменена. Собственная минимальная проба A показала, что `git worktree remove` без `--force` сам по себе удаляет ignored-файлы; новая регрессия проверяет их сохранение.

Копирование допускает только явные правила для ignored-файлов. Проверяются реальные пути, symlink, выход за корень, tracked-файлы, существующее назначение, служебные каталоги, лимиты и коллизии. Производственный выбор проекта пока возвращает пустой список правил; редактора правил в P5 нет. При откате скопированного файла проверяются dev/ino и digest: заменённый или изменённый пользователем файл сохраняется вместе с диагностикой неполного cleanup.

| B: constraint Store терял диагностическую причину | A сохраняет её в `store_constraint`, отдельно от отказа SQLite; регрессия проверяет диагностику и отсутствие эффекта |

| A: поверхностно frozen request оставлял изменяемые вложенные env/argv | B обходит все вложенные объекты; регрессия проверяет невозможность подмены перед исполнением |
| A: cleanup присваивал ресурсы с неизвестным исходом и не учитывал ignored-файлы | B сохраняет неоднозначные ресурсы и проверяет ignored только перед удалением; отдельные Git-регрессии проверяют обе границы |

Настоящее окно проверяет потерю create/send-ответа, reload, неизменный ID и отсутствие повторного эффекта |

Обратное ревью A подтвердило содержательность IPC/cursor/crash/UI-тестов и выявило доступную кнопку подтверждения при `actions.prepareSetup=false`, а также неоднозначность сообщений на границе страницы. C ограничил кнопку, добавил объяснение и регрессии completed+invalidated/revoke/reload в настоящем Electron; предупреждение границ истории также проверено. B не нашёл блокирующих замечаний в UI, но указал отсутствие engine-матрицы crash при `create_session`. C добавил пять случаев SIGKILL: after_intent, before_effect, after_effect, before_result, after_result с проверкой фактического worktree, единственной сессии, lease и отсутствия повторного вызова настоящего `createWorkspace`. ### Причина отказа автоматической приёмки

После передачи обычный `npm test` запускался оболочкой без пользовательского профиля. В ней `node` — `/opt/homebrew/bin/node` версии 26.11.0, тогда как интерактивная оболочка и `with-node.sh` выбирали закреплённый 24.15.0. Полный запуск под Node 24 прошёл даже без ограничения числа параллельных процессов; гипотеза о нагрузке не подтвердилась.

Отказ воспроизведён командой `npm test -- tests/git-p5.test.ts -t SIGKILL` в оболочке без профиля: три падения на `tests/git-p5.test.ts:306`. Дочерний Node 26 завершался с `bad option: --experimental-transform-types` до входа в аварийную точку; поэтому `child.signal` был `null`, а не `SIGKILL`. Это ошибка выбора runtime тестовой команды, не ошибка durable Git или SQLite.

`package.json` теперь запускает обе команды `test` и `test:node` через существующий `scripts/with-node.sh`, затем через прежнюю защиту `with-test-awake.sh`. Глобальные PATH/HOME/Node, ограничения `engines`, таймауты, число параллельных процессов и assertions не менялись. В `tests/test-command.test.ts` добавлены две поведенческие регрессии: впереди PATH находится собственный несовместимый Node, доступная закреплённая версия помещена в собственный временный каталог; проверяются выбор правильного runtime и буквальная передача аргументов. До исправления обе проверки падали, после него адресный набор вместе с `git-p5.test.ts` прошёл **19/19** в той же оболочке без профиля.
