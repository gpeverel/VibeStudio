## Конкретный результат

Исполняемый прототип: `tests/isolation/native/broker.ts`, `launcher.ts` и `tests/isolation/macos-native.probe.ts`. Он вызывает именно производственный ProcessRunner с `/usr/bin/sandbox-exec`, а не опирается на внешнюю песочницу Codex. Код намеренно остаётся лабораторией: обязательные границы не закрыты, production backend не подключён.

Команда немодельной лаборатории: `MACOS_NATIVE_PROBE=1 sh scripts/with-node.sh node --experimental-transform-types tests/isolation/macos-native.probe.ts`. Нужны технические права на loopback listen и отдельный Seatbelt, собственные tmp targets, установленный `/usr/bin/cc`. Compiler создаёт только свой C helper. Внешних соединений, CLI, Keychain и модели в этой команде нет. Положительный transport broker — явно локальный double, не фиктивная аттестация настоящего provider.

## Причина --help и минимальные auth/runtime исключения

В прежнем профиле CLI 2.1.295 падала **до авторизации**: `TypeError: Failed to format a number`. Контроль A без ICU вновь даёт exit 1, stdout 0, stderr 4983 байта. Контроль B отличается read-only доступом к `/usr/share/icu`: --help exit 0, stdout 22116 байт, stderr 0. На этой macOS там `icudt74l.dat` и `icutzformat.txt`. Установлена причина старта — закрытые системные данные форматирования ICU, а не несовместимость Keychain. Bundled-code excerpt из исходной ошибки отброшен; в fixture только диагностическая строка.

Диагностические исключения: системные библиотеки/программы и ICU, устройства random/null; точный бинарник; точные `~/.claude.json` и `.credentials.json`; в отдельной вариации read-only штатных каталогов Keychain, запись только в `/dev/null` и собственный tmp runtime. HOME и CLAUDE_CONFIG_DIR не менялись, credentials не переносились. TMPDIR у последней диагностики указывает собственный стенд, без переноса auth-state. Никакого writable доступа ко всему ~/.claude, домашнему каталогу или Keychain-файлам не добавлено.

Даже с Keychain-read и null sink `auth status` локально сообщает `loggedIn:false`, `authMethod:none`, exit 1. Причина **этого** результата не установлена, успешное normal-auth сочетание пока не найдено. В диагностике Mach IPC намеренно разрешён широко, поэтому она не доказывает минимальность IPC/auth и сетевую изоляцию. Token refresh, persistence и реальные runtime записи не проверены. Нельзя заключить, что штатная авторизация принципиально несовместима с native. После установления независимого обязательного stop-блокера расширение домашнего доступа ради поиска «зелёной» авторизации остановлено.

## Builtin и managed

[Официальный справочник](https://code.claude.com/docs/en/settings-reference#enabledplugins) описывает Boolean `enabledPlugins` по plugin-id; [per-run settings](https://code.claude.com/docs/en/settings#change-a-setting-for-one-session) допускает собственный JSON-файл выше user/project/local и ниже managed. Проверен файл собственного стенда:

```json
{"enabledPlugins":{"cc-plugin-agents-md@builtin":false,"cc-plugin-plugin-authoring@builtin":false}}
```

Он принимается --help и plugin list --json при запрете пользовательских записей. Inline JSON оказался другим путём: CLI пытается mkdir `/tmp/claude-<UID>` и падает EPERM. Исключение общего per-user tmp не добавлялось; выбран документированный файл.

**Это проверка принятия способа конфигурации, не отключения builtin.** plugin list --json выдаёт [] и с настройками, и без них. Его help не предоставляет флага builtin inventory. Поэтому [] этого subcommand не подменяет system init.plugins. Настоящего немодельного effective builtin/session inventory в выбранных командах не получено. Проверка пустого init.plugins в live-runner сохранена без blacklist. Постоянные enabledPlugins, managed-файлы и MDM не изменялись. Managed force-enable имеет приоритет: такой конфликт должен блокировать запуск, а не обходиться flags или запретом чтения политики. Отсутствие effective managed источников не доказано; широкие read-only исключения известных managed расположений в диагностике не являются их аттестацией.

[Anthropic](https://code.claude.com/docs/en/plugins/mods/overview#mods-built-into-claude-code) отличает agents-md (обработчики загрузки инструкций) от plugin-authoring (skill без mod-кода). Safe-mode/bare/disableAllHooks не отключают builtin. В четырёх старых реальных потоках доказана **регистрация** двух builtin; исполнение конкретного handler или загрузка skill не доказаны. Нельзя снять требование [] на основании отсутствия Skill/tool events.

## Модель угроз и привязка запуска

Защищаемся от операций CLI/проекта и порождённых ими процессов: все они должны наследовать ОС-профиль. Сканирование alias до запуска + отсутствие writable workspace у этих субъектов препятствуют внесению ими внешнего hardlink в проверенную область. Проект с уже существующими aliases получает отказ, а не обещание частичной защиты.

Отдельный злонамеренный **несандбоксированный процесс того же UID** может поменять inode между scan и spawn, внедрить alias в writable runtime или обратиться к локальному broker. Mode 0700 не защищает от владельца. Эти проверки такой процесс не изолируют. Это явно отдельная угроза, не тайное расширение требований SPEC и не утверждение её отсутствия. Для устойчивости к нему нужен иной владелец/защищённая файловая область; текущий prototype не аттестуется ни по одной трактовке, потому что независимый stop-критерий уже не выполнен. Обычные внешние изменения проекта также требуют атомарного launch snapshot/проверки идентичности в будущем backend.

Устранён конкретный дефект композиции adapter: раньше verified/evidence приводили к обычному runner.start. Теперь подтверждение должно предоставить доверенную launch-capability, и adapter вызывает именно её. Наличие evidence без launch даёт profile_unverified; отдельный регрессионный тест запрещает обращение к обычному runner после проверки. Это внутренний контракт, не IPC-флаг. Произвольный callback сам по себе не является доверием: production-реализация verifier отсутствует, laboratory launcher не возвращает verified. Все обязательные границы должны пройти до выдачи capability, включая managed/auth/profile/CLI hash и жизненный цикл broker.

## Конкретный блокер и минимальное изменение архитектуры

**Сочетание текущего ProcessRunner (POSIX process group), разрешённого fork у неизменённой CLI и Seatbelt не обеспечивает полную остановку.** Это доказано собственным fork/setsid helper под той же фактической политикой. Закрытие pipes/broker не убивает сбежавшего ребёнка; запрет файлов/сети не равен остановке. В [публичном исходнике Apple XNU](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_prot.c) setsid переводит подходящего ребёнка в новую группу; upstream source — пояснение механизма, локальная проба — доказательство именно этой macOS. Не утверждаем невозможность любой native-архитектуры или несовместимость Keychain.

Минимально необходимо заменить **владение одной POSIX-группой** на владение изолированным runtime с обеспеченной остановкой всех создаваемых процессов. Опрос PID/PPID не подходит как гарантия: reparent/setsid и гонки создания остаются. Альтернатива — запретить fork в процессе CLI и выполнять всю необходимую дочернюю работу через отдельно управляемые доверенные helpers; совместимость этого изменения со штатной CLI/Keychain/Read-Glob-Grep ещё не доказана, это новая интеграция, а не исправление таймаута. Для исследуемой неизменённой CLI не добавляем fork-deny как фиктивно рабочий профиль.

В разрешённых условиях **нет проверенного native механизма такого владения**, а установка служб, изменение ОС-политик и переподпись CLI запрещены без отдельного согласования. Поэтому текущая комбинация остаётся заблокированной. Решение пользователя, если сохранять весь SPEC и native: разрешить отдельную проработку нового механизма владения процессами/доверенных helpers; нельзя обещать, что простая служба или EndpointSecurity автоматически решит эту задачу. VM не внедрялась и повторно не предлагается как уже выбранное решение. Ослабление stop-требования не внесено.

Параллельные незакрытые gates: нормальная auth при минимальных исключениях, effective managed/builtin и полный provider-only broker. Они записаны точно, но для отказа уже достаточно воспроизводимого stop-контрпримера. Дополнительные модельные вызовы ни один из этих механизмов не исправят.

## Заключение fork-deny исследования, 2026-10-11

Последняя незакрытая гипотеза из предыдущего раздела проверена **конечным набором немодельных проб**, одним агентом. Production код/AccessVerifier не менялся; ни одного verified результата не добавлено. Службы, ОС-политики, подпись CLI, HOME/configDir и постоянные настройки не менялись. Переноса credentials нет. Модели/--print/prompts/login/--version/старый live-runner: **0 запусков**.

### Исполнение и результаты

### Кто создаёт ребёнка и зачем это обязательно

Инициатор — **сама неизменённая CLI**, реализация чтения credential document из Keychain, не проектный script/hook/MCP и не вызов инструмента модели. В установленном бинарнике найдена последовательность вызова `security` с операцией `find-generic-password`, флагами account/service и чтения значения. Значения account/service и credential output не извлекались и не сохранялись. Runtime PATH-wrapper зарегистрировал только заранее заданные operation/exit markers, передал исходные аргументы настоящему `/usr/bin/security` и его stdout непосредственно в штатный pipe CLI. Wrapper добавляет диагностическую shell-обёртку только в помеченных строках; чистый A/B авторизации выполнен **без** wrapper.

[Официальная документация Anthropic](https://code.claude.com/docs/en/authentication#credential-management) указывает Keychain как штатное хранилище macOS. SPEC §4 и §10 требуют диагностику/сохранение штатной авторизации; пользователь выбрал именно её. Получение сохранённого credential — обязательная операция для этой комбинации 0C, даже если Read/Glob/Grep вообще не создают детей. Без credentials разрешение запуска модели невозможно. Код 44 в ограниченном control означает результат helper, а не доказанную потерю логина: нормальный файловый control подтверждает, что login доступен. Точный заблокированный write/cache/Keychain ресурс остаётся неизвестным.

[Apple XNU fork1](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_fork.c) поясняет общую проверку создания fork/spawn. Это upstream исходник, не аттестация установленного ядра; доказательство EPERM именно на этой macOS — четыре реальные C-пробы. Не утверждаем проверку запуска через все Mach/launchd IPC: IPC-сервис мог бы создавать процессы вне прямого fork, и такой путь потребовал бы отдельной закрытой политики в production.

### Конечное решение по рассмотренным вариантам

1. **Текущая группа ProcessRunner + разрешённые дети:** опровергнута гарантия полной остановки (прежний реальный fork/setsid marker после done). Это не исправляется drain deadline, закрытием broker или подсчётом PID.
2. **Полный deny process-fork + неизменённая CLI 2.1.295 + текущий Keychain:** **опровергнута совместимость обязательной auth** чистым A/B. Help/plugin list работают, но этого недостаточно. Этот вариант не становится production launcher.
3. **Исключение «разрешим только security/rg exec»:** не является исправлением пункта 2. Сам fork/spawn уже запрещён до успешного запуска helper; добавление разрешения на executable не отменяет EPERM. Разрешить fork и ограничить exec — другая политика, которая сама по себе не предотвращает fork→setsid без exec. Она не закрывает пункт 1 и не проверялась как зелёная замена.
4. **Иной auth источник/credential broker либо другой CLI build с in-process Keychain:** в этой работе не проверялись и не внедрялись. Подстановка API/OAuth env из Keychain была бы переносом secrets/изменением auth-интеграции, а не сохранением исследованного штатного механизма. In-process Keychain требует другой реализации CLI; переподписывать/патчить установленный бинарник запрещено. Не обещаем совместимость остальных функций даже после такого изменения.

**Конкретно необходимое архитектурное изменение, если сохранить неизменённую CLI и штатный Keychain:** runtime должен допускать её обязательные helpers, но владеть **всеми** создаваемыми процессами независимо от POSIX группы/setsid. Значит, текущий ProcessRunner с владением одной группой нужно заменить обеспеченным backend изолированного исполнения: prepare возвращает принадлежащий запуску runtime-handle; start использует только этот handle; stopAll гарантирует прекращение всех его процессов до done и закрытия ресурсов; AccessVerifier выдаёт launch только для доказанного handle + file/network/config/auth профиля. Перечень PID/PPID или произвольный unprivileged supervisor не является реализацией этого контракта. В текущем разрешённом наборе macOS механизмов такой backend **не найден и не обеспечен**; простая служба также не объявляется решением без доказательства.

Если сохранить запрет всех детей, необходима другая auth/CLI интеграция, в которой Keychain обрабатывается **внутри** процесса, плюс отдельная проверка файловых инструментов. Это уже изменение исходной комбинации; установленный CLI не умеет заменить свой child helper предоставленным приложением in-process обработчиком через проверенные нами параметры. Выбор относится к архитектуре исполнения/авторизации, не к увеличению live-бюджета. Ни один из двух маршрутов не реализован сверх текущего согласованного прототипа. VM не внедрялась, этап 1 не начат.

### Что остаётся неизвестным и почему 0C не закрыт

- Read/Glob/Grep при fork-deny: **не проверены**; нельзя выводить работоспособность или необходимость rg-child из help/наличия строк бинарника. Нужна живая проверка реальных инструментов только в комбинации, прошедшей auth/изоляционный gate.
- Persistence/resume и замена инструкции: **не проверены в fork-deny**. Прежние успешные 01–03 подтверждают протокол/сохранение/resume в прежней среде, не новый профиль и не замену инструкции.
- Effective managed/builtin, точные runtime-write исключения со штатной auth, атомарная inode-область и полный provider-only с auth/IPC/TLS: **остаются открыты**. Постоянные settings/managed не менялись; [] в plugin list не подменяет требование [] в init.plugins.

Итог исследования завершён, но **0C не завершён**: fork-deny shortcut исключён из рабочих вариантов, а обеспеченного backend для неизменённой CLI/Keychain нет. `profile_unverified` сохранён; нового цикла общих исследований или модельных запусков не начато.
