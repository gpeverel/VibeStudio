## 1. Границы продукта и решения

Личное локальное приложение для macOS. Первая полезная версия поддерживает установленные Claude Code и Codex CLI со штатной авторизацией. Адаптеры можно реализовывать последовательно. Приложение не реализует собственный вход к провайдерам, не переносит токены в своё хранилище и не обновляет CLI молча. VM, обязательные контейнеры, гостевая ОС и тяжёлая дополнительная инфраструктура исключены. Службы с привилегиями, переподпись CLI и изменения политик macOS не являются штатным решением.

| Тема | Решение |
|---|---|
| Стек | Сохранить текущий Electron + TypeScript strict + React + electron-vite как рабочую основу; npm, Node 24 для разработки. Electron допустим, но не обязателен по инерции: качество и ресурсы обосновываются измерениями. Смена стека требует отдельного обоснования и согласования |
| Агенты | Отдельные Claude/Codex адаптеры над существующим ProcessRunner, процесс на ход и CLI resume. Конкретные argv/форматы/session IDs проверяются отдельно для каждого CLI; Claude-флаги не переносятся в Codex по аналогии |
| Хранение | SQLite через `better-sqlite3`, SQL-миграции; локальные диагностические JSONL-журналы в `~/Library/Application Support/<App>` |
| Git | Системный Git через аргументы `execFile`, без shell для Git-команд; worktree создаёт приложение |
| Применение | Squash в явно выбранную локальную базовую ветку; одна успешная операция применения на workspace в MVP; повтор того же запроса идемпотентен |
| Отмена применения | Отдельный отменяющий коммит с сохранением последующих коммитов пользователя; без автоматического `reset --hard` |
| Тесты | Vitest для проекта, существующий Node-runner сохраняется; Git — настоящие временные репозитории; CLI-парсер — обезличенные реальные записи |
| Дизайн | Один файл токенов и переиспользуемые компоненты; минимализм, один сдержанный акцент, анимации до 150 мс |

Приложение не добавляет собственной телеметрии и фоновой отправки содержимого проектов. CLI обращаются к провайдерам; согласованные команды могут обращаться к сети. Практический профиль не гарантирует `provider-only`. Git push и публикация требуют отдельной авторизации и не следуют из разрешения setup/тестов. Формулировки «всё работает без передачи наружу» и «полная изоляция» недопустимы.

Первая полезная версия (MVP) включает Claude и Codex, Solo и базовый Swarm, семь режимов задачи, проверки, ревью, commit/push/apply/discard, восстановление и несколько сессий. Базовый Swarm — несколько участников, сообщения, согласование владения работой и общий результат; весь набор режимов VibeForge копировать не требуется. Fusion, Orchestrator, дизайн-режим, интеграции skills, голос, iPhone, SSH, Windows, автоматический агент-ревьюер и отдельный режим «Проверка» отложены. Не создавать универсальную платформу стратегий ради двух нужных сценариев.

### Пользовательский сценарий

1. Выбрать Git-проект, проверить среду, базовую ветку и профиль доверия.
2. Создать сессию и выбрать режим. Приложение показывает, от какого коммита будет создана worktree и что незакоммиченное из основной копии не переносится автоматически.
3. Создать workspace и checkpoint; подготовить рабочую копию по согласованному набору команд, без обещания ОС-изоляции.
4. Запустить ход; показывать текст, инструменты и состояние; дать остановить работу.
5. Проверить результат и при необходимости выполнить ограниченный цикл исправления.
6. Показать дифф, новые файлы и замечания; после правок пометить предыдущие проверки устаревшими.
7. Commit и Push — отдельные действия. Для «Применить» интегрировать актуальную базу в workspace, повторно проверить полученный результат и показать обновлённое ревью.
8. Применить проверенную ревизию либо явно обойти проверки. «Отбросить» и «Отменить применение» — разные операции.

## 2. Архитектура и общие контракты

Один пакет, границы проверяет dependency-cruiser:

```text
src/
  shared/    DTO, типы и zod-схемы IPC/событий; без Node/Electron и бизнес-логики
  core/      домен, SessionEngine, SoloStrategy, SwarmStrategy, порты, режимы
  adapters/  claude, codex, git, process-runner, workspace-files, store, journal
  main/      сборка зависимостей, preload, IPC, окна
  renderer/  React, токены и компоненты; доступ к приложению только через window.api
```

`core` зависит только от `shared` и собственных портов. Zod разрешён в `shared`; определение «shared без любых зависимостей» не используется. Runtime-доступ к fs/process/sqlite/Electron находится в адаптерах и main.

Порты: `AgentAdapter`, `GitPort`, `ProcessRunner`, `WorkspaceFiles`, `Store`, `Journal`, `Clock`, `IdGen`. Общие типы живут в производственном коде; тесты импортируют их, но проверяют независимые поведенческие ожидания. Исключить `Promise<unknown>` для известных результатов и свободный `string` для доменных кодов ошибок.

Нормативные поля запросов запуска: `sessionId`, `turnId`, `participantId`, `workspaceId`, `cwd`, `prompt`, `agentSessionId`, `resume`, явно выбранный версионированный `profile`, `model`, поддерживаемые ограничения ходов и разрешённые переменные окружения. Выбор адаптера закреплён за participant; ID диалога принадлежит конкретной CLI и не переносится между ними. Профиль различает политику инструментов/расширений, согласие на доверенный проект и фактически обеспеченные ограничения. Пути workspace и защищаемых приложением ресурсов сами по себе не являются ОС-границей.

`AgentAdapter.detect()` возвращает доступность установленной CLI: путь, версию, состояние авторизации, объявленные возможности и причины недоступности. Объявление в help и проверенное поведение различаются. Допуск конкретного профиля оценивается отдельно от detect. `start()` возвращает события, идемпотентные `interrupt()`/`kill()` и `done`. `done` завершается после выхода/закрытия потоков либо конечного таймаута с явным результатом завершения; он не доказывает отсутствие всех потомков. Итог публикуется ровно один раз; ошибка запуска — доменный результат.

Старый `AgentCapabilities.readOnly: verified` и `AccessVerifier` относятся только к прежнему строгому обещанию. В новом практическом профиле этот статус не выдаётся: доступность CLI, допуск профиля и пределы гарантий — разные данные. Старая форма запроса без нового явного вида профиля сохраняет строгий смысл и прежний отказ без verifier. Нельзя молча преобразовать её в практическую или переключиться на более широкие полномочия после ошибки.

### SessionEngine и идемпотентность — P0

- Все пользовательские команды имеют `requestId`; повтор возвращает существующую операцию, а не создаёт второй процесс или применение.
- Один активный ход на participant. Solo имеет одного писателя workspace. В базовом Swarm параллельное чтение допустимо, изменяющие ходы общей worktree сериализуются приложением; владение задачами/файлами согласуется сообщениями. Это минимальное инженерное решение первой версии, не ОС-блокировка и не требование запускать всех одновременно. Setup, проверки, commit/apply/discard не пересекаются с агентными записями.
- SQLite хранит намерения и состояние приложения. Переход состояния и нормализованное событие фиксируются одной транзакцией; UI уведомляется после commit и может дочитать события по курсору.
- Перед внешним эффектом записывается `operationId` и намерение. После него — результат. SQLite и Git/процесс/файловая система не образуют одну транзакцию: при старте требуется сверка.
- JSONL — диагностика, не второй источник бизнес-состояния. Не обещать атомарность JSONL и SQLite или воспроизводимость потерянного при аварии хвоста.
- SQLite подтверждает намерение; Git и файловая система подтверждают фактический эффект. Не объявлять всю БД вторичной относительно одного ref.

Основные переходы:

| Состояние | Событие | Результат |
|---|---|---|
| В очереди | Получен слот | Подготовка или запуск следующего хода |
| Подготовка | Успех / ошибка | Работает / Ошибка среды |
| Работает, Исправление | Терминальный результат | Проверка, Нужно разрешение, Ошибка среды или Прервано по типу результата |
| Проверка | Успех | Готово к ревью; отсутствие проверок явно отображается |
| Проверка | Падение, бюджет исправлений есть | Исправление |
| Проверка | Бюджет исчерпан / повтор ошибки | Проверки не прошли |
| Готово к ревью | Новое замечание или изменение | Новый ход / устаревшие проверки |
| Готово к ревью, Проверки не прошли | Допустимое применение | Применяется; обход проверок требует отдельного подтверждения |
| Применяется | Подтверждённое завершение / неоднозначность | Применено / Применение прервано |
| Любой активный процесс | Stop | Останавливается; затем Остановлено в пределах управляемого запуска либо Остановка не подтверждена / Ошибка остановки (§4) |
| Активная операция | Падение приложения | Сверка; Прервано или Применение прервано без автоматического повтора |
| Неактивный workspace | Подтверждённое удаление | Отбрасывается, затем Отброшено |

Read-only ход после успеха переходит к ответу/ревью без автоматического запуска изменяющих проверок. Поздний `run_finished` после принятого stop сохраняется в истории, но не запускает исправление или проверки. Конфликт базы имеет отдельное состояние «Конфликт»: применение заблокировано до его разрешения и новых проверок. Полная таблица событий и запретов закрепляется тестами автомата до подключения реального агента.

## 3. Права, доверие и окружение — P0

### Принятая модель доверия

Практический локальный профиль предназначен для доверенных проектов. Используются ограничения инструментов CLI, явное управление расширениями, worktree и проверки операций приложения. Обязательная собственная ОС-песочница исключена из условий первой версии. Это не полный доступ по умолчанию и не прежний строгий verified-профиль.

Ошибки модели сдерживаются ограничением действий, ревью и отдельным применением. Вредоносные инструкции проекта не считаются безопасными из-за наличия worktree. Scripts/hooks/MCP/plugins — исполняемый код, включение которого требует явной политики. Установленная CLI и её необходимые штатные helpers входят в доверенную цепочку; auth-helper не приравнивается к произвольной команде модели. Защита от злонамеренного стороннего процесса того же UID не обещается.

Практический профиль не гарантирует невозможность чтения/записи за пределами worktree, изоляцию общего Git-каталога, сеть только к провайдеру или остановку всех отделившихся потомков. Ограничения и конфликты показываются пользователю. Недоверенный проект нельзя выдавать за безопасный после закрытия предупреждения. Лаборатории сильной изоляции сохраняются отдельно, без обязательной зависимости production от Seatbelt/broker/hardlink scan.

### Режимы

| Режим | Политика |
|---|---|
| Агент, Поиск бага, Тесты | Целевая область правок — workspace; ограниченный набор инструментов и согласованных команд. Scripts запускаются по правилам согласия ниже; ОС-граница их действий не обещается |
| План, Опрос, Вопрос, Ревью | Закрытый набор инструментов чтения; без Bash, записи, произвольных MCP и делегирования инструментам с более широкими правами |

Для Claude `allowedTools` разрешает вызовы без запроса, но не ограничивает доступный набор: задаётся явный `--tools`, MCP ограничиваются отдельно. `dontAsk` не отменяет ранее выданные разрешения. Codex получает собственную проверенную реализацию политики, а не копию этих флагов. Название read-only в практическом профиле означает закрытый набор операций чтения, не запрет всех файловых эффектов процесса средствами ОС. Исключение Edit/Write/NotebookEdit само по себе не доказывает такой запрет.

Проектные hooks/MCP/plugins и исполняемые настройки не включаются молча; профиль по умолчанию требует их отключения доступными средствами конкретной CLI. В 0C проверить выбранную комбинацию ограниченного режима, источников settings и отключения расширений. Не считать одного флага доказательством effective-конфигурации. Известный конфликт managed-политики или неподдерживаемая обязательная настройка блокирует этот запуск с объяснением; внешнюю политику не обходить. Неизвестные данные не заменять пустым списком. Непроверенная обязательная предпосылка остаётся причиной недопуска, но не требует доказательства отсутствия всех мыслимых механизмов ОС.

Builtin inventory рассматривается отдельно от проектных расширений. Регистрация builtin не доказывает исполнение, но и отсутствие tool events не доказывает отключение. Требование `init.plugins == []` остаётся историческим критерием строгого профиля; практический фиксирует известный состав, роль и ограничения совместимой версии CLI. Не добавлять blacklist/игнорирование неизвестного builtin ради прохождения. Init после старта не является превентивным запретом hooks. `--bare` и отключение fork не являются универсальным решением; штатная авторизация проверяется отдельно.

Включение проектной конфигурации — осознанное изменение профиля с перечнем исполняемых расширений; соответствующие согласия и проверки при существенных изменениях устаревают. Выбор практического профиля делается явно доверенной композицией приложения по сохранённому пользовательскому решению, не флагом verified от renderer или инструкцией модели.

Приложение проверяет пути и принадлежность ресурсов для собственных операций, бережёт основную копию и конфигурацию при copy/apply/discard. Worktree не является песочницей; общий Git-каталог остаётся отдельным ресурсом. Нельзя приписывать эти проверки произвольному коду CLI/scripts. Предполагаемые области операций и необходимые служебные записи описываются отдельно от реально обеспечиваемых ограничений.

Запреты `rm`, `curl`, `git push` и т.п. — дополнительная политика, не файловая/сетевая изоляция. Разрешённый интерпретатор или npm-script может менять внешние файлы и отправлять данные. ProcessRunner управляет запуском, таймаутами и потоками; он не превращает setup/проверки в sandbox. Если в будущем заявляется более сильная гарантия, для неё требуются отдельный обеспечивающий механизм и доказательства, без автоматического изменения практического профиля.

### Согласие на setup и проектные scripts

Для проекта сохраняется согласованный набор команд: операция/назначение, argv или явно выбранный script, cwd, значимые права/окружение и идентичность исполняемого содержимого. Повтор обычной проверки при неизменных существенных условиях не требует нового вопроса. Изменение команды, содержимого согласованного script (включая известные вызываемые проектные scripts), прав или назначения инвалидирует согласие до запуска. Одного совпадения строки `npm test` недостаточно. Если значимые исполняемые входы нельзя установить, приложение не выдаёт бессрочное согласие на произвольный код: ограничивает область допуска и объясняет недостающие данные. Это проверка актуальности решения пользователя, не полная аттестация всей цепочки зависимостей.

Публикация, push и разрушительные операции не входят автоматически в разрешение setup/тестов. Ни широкое разрешение Bash, ни согласие с доверием проекту не должны обходить эти границы. Для запуска через инструмент агента адаптер должен уметь применить согласованную политику; если CLI не позволяет это обеспечить, соответствующий путь не включается, а проверка запускается приложением как именованная согласованная операция.

### Отказы и расширение прав

`permission_denied` содержит инструмент, безопасное превью входа, причину, область и источник правила. Различать отсутствие allow, пользовательский deny и неизменяемую внешнюю политику. Deny имеет приоритет над allow; кнопка «Разрешить и повторить» не обещает снять deny добавлением разрешения.

Разовое расширение по умолчанию действует на следующий ход; отдельно доступны область сессии и постоянное правило проекта. Для изменения собственного deny требуется явное редактирование этого правила. Внешние ограничения не обходятся. Новый ход — продолжение диалога, а не гарантия точного повторения только отвергнутого вызова; ранее успешные побочные эффекты не воспроизводятся автоматически.

Вопросы агента в неинтерактивном режиме отображаются текстом; пользователь отвечает следующим ходом. Не рассчитывать на интерактивный AskUserQuestion.

### Подготовка workspace

- Конфигурация проекта хранится в БД: база, setup, явные правила копирования, проверки, таймауты, политики доступа, сеть, лимиты исправлений и ресурсов. На запуск сохраняется версия конфигурации.
- `.env` копируется только по явному правилу пользователя; не попадает автоматически в Git, журнал или тестовые образцы. Передача содержимого агенту регулируется отдельно от доступности окружению проверок.
- Изменяемые симлинки из workspace в основную копию запрещены по умолчанию. `node_modules` устанавливается в workspace либо используется проверенная изолированная схема кеша; общий изменяемый симлинк не считается безопасной оптимизацией.
- Пути копирования проверяются после разрешения симлинков; запрещены выход за разрешённый корень, перезапись tracked-файлов и неожиданные коллизии. Повтор setup должен быть явно безопасен либо требовать нового workspace.
- Runtime-файлы имеют явный перечень и правила исключения из commit/diff. Не ослаблять общую проверку грязного дерева и не игнорировать все untracked ради `.env`. Если безопасное исключение настроить нельзя, подготовка блокируется с объяснением. Не менять общий ignore основной копии незаметно.
- В практическом read-only проверяются настройки инструментов и наблюдаемые эффекты на контрольном стенде; неизменность контроля не доказывает абсолютную невозможность иных записей. Собственные журналы и штатные CLI/auth-записи допускаются по описанной политике и не маскируются обещанием «ни одной записи».

## 4. Процессы, протокол, журналы и диагностика — P1

### Обнаружение и запуск

Каждый адаптер проверяет разрешённый абсолютный путь CLI, версию и поддерживаемую диагностику штатной авторизации, включая запуск `.app` из Finder с другим PATH. Для Claude уже используется `auth status`; способ Codex подлежит отдельной проверке, не выдумывается. Можно выбрать бинарник вручную; никаких молчаливых установок/обновлений CLI и чтения секретов приложением. Не копировать всё окружение Electron в процесс: задавать документированный набор переменных, сохраняя штатную авторизацию и её необходимые helpers.

Исторические пробы Claude относятся к версии 2.1.295. Фактическая поддержка каждого профиля определяется используемыми возможностями и проверенным поведением в 0C, а не одним номером версии. Неизвестную версию проверять совместимыми пробами; при отсутствии обязательной возможности отказывать без расширения прав. Обновление CLI инвалидирует относящиеся к ней выводы совместимости; автоматическая установка или обход запретов не являются fallback.

Сохранять UUID сессии приложения до первого запуска. Новый ход получает отдельный `turnId`; CLI-идентификатор может быть задан приложением или получен из протокола конкретного адаптера. Продолжение использует ID того же адаптера; формат UUID Claude не навязывается Codex. Не смешивать ID приложения, CLI-диалога и процесса. Передавать большие промпты через stdin, не строить shell-команду конкатенацией.

### Поток и итог

Нормализованные события: `run_started`, `text`, `tool_started`, `tool_finished`, `permission_denied`, `retry`, `usage`, `rate_limit`, `run_finished`. Конверт содержит `schemaVersion`, `eventId`, `sessionId`, `turnId`, `participantId`, монотонный в рамках сессии `seq`, время. У инструмента есть стабильный `toolCallId`; у текста — ID сообщения и явный тип delta/snapshot. Не удваивать текст при поступлении полного сообщения после дельт.

Итоги: success, error, max_turns, interrupted, limit. Причины ошибок включают отсутствие авторизации, лимит, сеть, перегрузку, несовместимый протокол и неизвестную причину. Не выдумывать время сброса лимита, если CLI его не сообщил.

- Парсер переживает разбиение UTF-8 и JSONL по произвольным порциям stdout; stderr обрабатывается отдельно и ограничивается по размеру.
- Неизвестное событие сохраняется как диагностика без падения всей сессии. Повреждённое обязательное событие не превращается в успех.
- Success требует согласованного терминального результата и завершения процесса. Отсутствие result, ненулевой exit после success, таймаут закрытия или принятый stop не дают «Готово» автоматически.
- Ограничить размер строки, очереди и журнала; предусмотреть обратное давление, пакетные уведомления UI и загрузку истории частями. Превышение лимита/ошибка записи завершают ход контролируемой ошибкой, а не бесконечным потреблением памяти.
- Токены и время сохраняются по ходу; итоговая usage не суммируется повторно с дельтами. Доллары — только оценка. Неизвестные значения показываются как неизвестные.

### Остановка и восстановление процессов

Агент, setup и каждая проверка имеют идентичность запуска. Stop: мягкое завершение основного процесса/принадлежащей запуску группы, конечное ожидание, принудительный сигнал в пределах доступного механизма, ограниченное дренирование потоков. Повтор безопасен. Таймауты различаются по типу операции; бесконечное ожидание ввода запрещено. Не искать и не убивать процессы по имени/строке команды. Отделившиеся потомки могут остаться; «все процессы завершены» без подтверждения не показывается.

Результат хода и результат завершения различаются: фиксируются подтверждённый exit основного процесса, результат отправки сигналов, закрытие потоков/таймаут, ошибки и предел проверки потомков. Принятый stop запрещает success и автопродолжение, но не стирает ошибку завершения. Даже если done завершён по deadline, это «Остановка не подтверждена»/«Ошибка остановки», а не успешная очистка.

При ошибке или неподтверждённом завершении не освобождать изменяющий слот workspace для нового хода/setup/apply/discard автоматически; сохранять проблему и диагностику. Разрешены повтор безопасного Stop для всё ещё подтверждённого владения и явная сверка/разбор. После подтверждения выхода управляемого процесса и завершения потоков штатная работа может продолжиться с постоянной оговоркой об отделившихся потомках; невозможность доказать их полное отсутствие сама по себе не блокирует каждый следующий ход. После crash нельзя считать прежний PID достаточным подтверждением владения.

Сохранять PID, время создания процесса по данным ОС, исполняемый файл, cwd и доступную идентичность группы/запуска. PID и совпадения командной строки недостаточно. После перезапуска сначала проверить принадлежность: неоднозначный процесс автоматически не завершать и не запускать рядом второй изменяющий процесс.

Восстанавливать все незавершённые операции: создание workspace, setup, ход, исправление, проверки, применение, отмену и удаление. Недоступный/удалённый CLI-транскрипт означает невозможность resume; предложить новый ход с явным указанием потери контекста. Не повторять команду setup, push или применение только на основании статуса «Прервано».

### Хранение журналов

Сырые строки могут содержать код и секреты. Журналы локальные, с ограниченным доступом, размером и сроком хранения; экспорт только по запросу, с очисткой чувствительных данных. В репозиторий попадают только обезличенные fixtures из одноразовых проектов. Очистка/усечение диагностического журнала не удаляет историю операций из БД. Очищенный журнал может быть недостаточен для точного воспроизведения парсера — это явно обозначается.

Ошибка записи состояния в SQLite блокирует новые побочные эффекты и инициирует безопасную остановку активного процесса. Не продолжать работу, если приложение больше не может записывать намерения и исходы.

### Создание, diff и commit

- Отсутствующий Git, каталог без репозитория и репозиторий без коммитов дают разные ошибки среды. `git init` допустим только по отдельному подтверждению; для сессии нужен хотя бы один коммит. Приложение не создаёт первый пользовательский коммит автоматически.
- `baseRef` разрешается в конкретный SHA один раз при создании. UI показывает выбранную базу. Грязная основная копия не переносится; staged/unstaged/untracked пользователя сохраняются.
- `refs/vibestudio/<sessionId>/base` создаётся только при отсутствии и не переписывается. Ошибка после создания ветки/worktree оставляет восстанавливаемую запись; удалять можно только доказанно созданные этой операцией ресурсы без новых пользовательских данных.
- Detached HEAD допускает работу от SHA, но без автоматического применения в текущую копию. Удалённая базовая ветка требует нового явного выбора и повторных проверок.
- Diff включает tracked-изменения относительно выбранной базы ревью и список новых untracked-файлов. Runtime-файлы исключаются по явной политике. Бинарные/слишком большие файлы показываются списком без неограниченного чтения; переименования и стороны diff сохраняются.
- Commit не делает безусловный `git add -A`: пользователь видит состав результата; секреты и runtime-файлы не включаются автоматически. Проверить настроенного автора, состояние merge/rebase и политику подписания до изменяющих шагов.
- Автоматические служебные операции по умолчанию не исполняют Git-hooks проекта; UI сообщает это и не выдаёт встроенные проверки за эквивалент hooks. Обязательное для проекта подписание, которое приложение не может выполнить, даёт отказ, а не молчаливое отключение требования.
- Подмодули и LFS в MVP не поддерживаются: инспекция показывает предупреждение, изменяющий запуск и применение блокируются. Не продолжать с неполной копией как будто это обычный проект.

### Контракт применения

Существующий `applyWorkspace` разделить на подготовку кандидата и применение проверенного кандидата; названия методов можно уточнить, но границы обязательны. Приложение не должно проверять старую ревизию, а затем скрыто изменять её слиянием внутри apply.

1. Получить блокировку на canonical Git common-dir внутри приложения и исключить других писателей workspace. Не считать её блокировкой внешнего Git/редактора.
2. Проверить явную связь session/workspace/repository/branch, чистоту основной копии (индекс, tracked и untracked), отсутствие merge/rebase/cherry-pick и нужную текущую ветку. Проверить автора/среду коммита заранее. Не переключать основную копию самостоятельно.
3. Сохранить ожидаемые base/head SHA. Интегрировать базу в workspace; конфликт остаётся там и требует явного разрешения. После разрешения завершить merge и заново подготовить кандидата.
4. Зафиксировать кандидат: commit/tree и `revisionId`; запустить проверки из §7, показать обновлённый diff. Если база, кандидат или конфигурация проверок меняются, подготовка и подтверждение устаревают.
5. Перед изменением основной копии сохранить durable intent с operationId, expectedBaseSha, candidateSha/tree, ожидаемой веткой, данными проверок и подтверждения. Если деревья базы и кандидата совпадают, завершить операцию как `no_changes`: показать «Нет изменений для применения», не помечать сессию применённой, не создавать коммит или checkpoint. Иначе создать без перезаписи checkpoint `refs/vibestudio/<sessionId>/operations/<operationId>/pre-apply`. Ref сам по себе не доказывает успешное применение.
6. Выполнить выбранный протокол, записывая фазы и результаты. Повтор requestId возвращает ту же операцию и не перезаписывает checkpoints. Если состояние изменилось после подготовки, вернуть соответствующий отказ, а не подменять подготовленного кандидата.
7. «Применено» означает согласованность итогового HEAD, дерева индекса, tracked-файлов и отсутствие незавершённой Git-операции. Нельзя делать вывод только по HEAD. Записать appliedSha и факт завершения; после успеха workspace больше не редактируется. Для следующего изменения создаётся новая сессия от актуальной базы.

Поля результата должны различать `applied`, `no_changes`, `interrupted`; доменные отказы включают dirty_tree, base_changed, candidate_changed, merge_conflict, checks_stale, invalid_workspace, operation_in_progress. Они доступны ядру без импорта GitError из адаптера.

Основание алгоритма уже реализовано и проверено в 0B в пределах одного процесса/in-memory Store (см. его отчёт); не заменять его новым рецептом без причины. Интеграция с durable intent и восстановление после реального падения ещё требуют проверки. `update-ref` не обновляет индекс и файлы; ни SQLite, ни marker-ref не делают всю последовательность атомарной. Сохранять тесты окон сбоя и проверки отсутствия потери изменений.

Восстановление сверяет intent, ожидаемые SHA/tree, фактические refs, индекс, tracked/untracked и незавершённые Git-операции. Однозначно завершённое применение дописывается в БД. Однозначно не начатое не повторяется само. Частичный или неоднозначный результат получает «Применение прервано» с диагностикой и безопасным действием; не выполнять автоматический reset/clean/stash. Последующие внешние коммиты или правки не перезаписываются.

### Отмена, удаление и push

- Отмена применения — новая журналируемая операция, создающая обратный коммит к конкретному appliedSha. Сначала подготовка и разрешение конфликтов в отдельном workspace, потом тот же протокол проверки/применения. Более поздние пользовательские коммиты сохраняются. Повтор запроса отмены не создаёт второй обратный коммит.
- Checkpoint хранит исходное состояние для диагностики/восстановления, но не даёт разрешения перемотать ветку пользователя.
- Существующие refs старого формата `refs/vibestudio/<sessionId>/pre-apply` при переходе на новый протокол сохраняются. Не считать такой ref свидетельством применения без сверки; неоднозначную старую операцию показать для ручного разбора.
- «Отбросить» удаляет только принадлежащие сессии ресурсы после остановки процессов и показа незакоммиченного/неопубликованного. Нельзя удалять по одному строковому префиксу пути; разрешить realpath и проверить реестр worktree. Применение в основной копии от discard не отменяется.
- Push принимает выбранное имя из настроенных remotes, а не произвольный URL/путь от renderer. До выполнения проверить фактический push URL и допустимый транспорт, показать пользователю цель и ветку; изменение назначения требует нового подтверждения. Произвольные external helpers не включаются молча. Локальный bare remote разрешён для тестов.
- Явный refspec и no-force сохраняются. Non-fast-forward даёт понятный отказ. При таймауте результат может быть неопределённым: проверить удалённый ref перед повтором, не объявлять операцию однозначно неуспешной. Удалённая ветка создаётся обычным подтверждённым push.

## 7. Проверки конкретной ревизии — P0

Проверки идут последовательно в workspace, каждая с собственной идентичностью процесса, таймаутом, ограниченным логом и обязательностью. Обязательные и необязательные результаты различаются. Отсутствие настроенных проверок — «Проверки не настроены», не зелёный успех; применение требует явного обхода.

`revisionId` идентифицирует точное проверяемое состояние: candidate tree/commit либо fingerprint tracked и релевантных untracked-файлов до коммита. Один HEAD не описывает грязный workspace. Вместе сохраняются версия конфигурации проверок, профиль среды и необходимые зависимости. Изменяемые runtime-входы учитываются отдельно; явно исключённые логи не должны сами инвалидировать результат.

Любая правка агентом/пользователем, новый commit с другим деревом, интеграция базы, изменение проверок или их значимых входов делает прошлый результат устаревшим. Проверка, которая сама меняет исходники, не подтверждает исходную ревизию: обновить кандидат и проверить заново. На время набора проверок исключить писателей приложения; внешние изменения обнаруживать сравнением состояния.

После падения агент получает ограниченный очищенный хвост лога с именем проверки. `maxFixAttempts` — число исправляющих ходов после первой проверки, не число всех запусков; начальное значение 2. Счётчик сохраняется и не сбрасывается перезапуском приложения. Одинаковая нормализованная сигнатура падения одной проверки дважды подряд останавливает цикл; исключаются время, случайные временные пути и ANSI, но сохраняется смысл ошибки.

«Применить без проверок» подтверждает конкретного кандидата и причину обхода, записывается в историю; не обходит грязное дерево, конфликт, чужой workspace или ограничения прав. Перед окончательным изменением основной копии ещё раз проверяются кандидат и актуальность результатов.

## 8. Ревью, IPC и UI — P1

### Замечания

Комментарий хранит workspace, revisionId, путь, сторону old/new, номер и контекст строки. Повторная привязка учитывает diff/переименование; одинаковый текст в разных местах не даёт права выбирать произвольно. При неоднозначности комментарий становится устаревшим и сохраняет исходный контекст.

Статусы «открыто», «решено» и «устарело» различны. Исчезновение строки не означает решение. Открытые замечания отправляются следующим ходом одной пачкой, включающей ревизию; успешный ход не закрывает их автоматически. Состояние проверок после правок пересчитывается.

### Граница IPC

`contextIsolation: true`, `nodeIntegration: false`, строгий CSP, узкий preload API и проверка DTO через zod. Main проверяет источник IPC, принадлежность session/workspace/project и допустимость операции в текущем состоянии. Renderer передаёт ID, main разрешает сохранённые пути; валидная форма произвольного пути или команды не даёт разрешения их выполнить.

Команды проекта настраиваются через отдельный пользовательский сценарий с валидацией и подтверждением, а не универсальный IPC «exec». Ответы агента, имена файлов, Markdown и логи считаются недоверенным содержимым: без исполнения HTML/скриптов, произвольной навигации и загрузки внешних ресурсов из сообщения. Открытие внешних ссылок допускает только разрешённые схемы и явное действие пользователя.

### Дизайн и доступность

Использовать существующие `docs/DESIGN.md`, `src/renderer/styles/tokens.css` и компоненты. Нужен современный локальный интерфейс, хорошие светлая/тёмная темы, плавные короткие анимации до 150 мс с учётом reduced motion, нормальная интеграция с macOS: клавиатура/меню, фокус, открытие файлов и корректный жизненный цикл окна. Переиспользовать палитру, типографику, отступы и состояния; без случайных градиентов, декоративных emoji и новых шкал. Контраст и ошибки не выражаются только цветом. AppKit/SwiftUI не обязательны; качество Electron обосновывается на рабочих сценариях.

Лента и diff загружаются порциями, большие файлы ограничиваются с объяснением. UI восстанавливает события по курсору после переподключения. Экран ревью явно различает «Готово к ревью», «Проверки устарели», «Проверки не прошли», «Применяется» и «Применение прервано». Выбор diff-библиотеки производится небольшим прототипом с комментариями, rename и большими файлами; конкретная библиотека пока не обязательна.

## 9. Параллельность и уборка — P1

До этапа 5 активен один изменяющий запуск. Далее общий лимит активных агентных участников по умолчанию 3, включая Solo и Swarm, остальные в очереди. Setup и проверки учитываются в общем бюджете процессов и не обходят его. Планирование — FIFO с отменой ожидания; в общей worktree изменяющие операции дополнительно сериализуются. Лимит 3 — стартовый параметр для измерения, не обещание допустимого расхода.

Порты выделяются через `port_leases`, проверяются на доступность и передаются как `PORT`, `VIBESTUDIO_PORT_1…`. Проверка свободного порта не гарантирует его будущую доступность: ошибка bind должна давать контролируемое переназначение/повтор. Порт не освобождается, пока подтверждённо жив процесс-владелец; после аварии требуется сверка. Жёстко заданные 3000/5173 не использовать.

Приложение имеет одного владельца операций с данными либо межпроцессную защиту от второго экземпляра. Применения сериализуются по Git common-dir, а не только по пути checkout. Это не защищает от внешнего Git.

При старте сверяются БД, операции, реальные worktrees и процессы. «Сирота» показывается с владельцем, состоянием и причинами неопределённости. Незакоммиченное и неопубликованное не удаляется автоматически. Удаление workspace не удаляет автоматически транскрипты CLI, checkpoints и историю применения; сроки хранения определяются отдельно.

### Базовый Swarm — обязательная часть первой полезной версии

Несколько участников с выбранными Claude/Codex адаптерами работают над одной целью. Нужны roster, фаза согласования владения, адресные/общие сообщения, сохранённые решения, продолжение диалогов и один общий результат со ссылками на вклады и нерешённые разногласия. Роль сборщика результата не превращается автоматически в отдельного привилегированного агента. Протокол не требует, чтобы все участники были одной CLI.

Сообщения имеют ID, отправителя, адресата, статус доставки и порядок; повтор/перезапуск не должен дублировать эффект. Для неактивного участника используется mailbox и следующий ход resume; мгновенная доставка поддерживается только при подтверждённой способности CLI. Фазы и раунды конечны. Stop всей сессии отменяет очередь, останавливает активные управляемые запуски и показывает результат по каждому; ошибка участника не прячется за общим успехом. После Stop новые сообщения не запускают автоматическое продолжение.

В первой реализации общая worktree получает не более одного изменяющего хода одновременно; участники могут параллельно исследовать её в режиме чтения. Владение файлами — протокол координации и проверок конфликтов, не sandbox. Изменение этой модели параллельной записи — отдельное решение после измерений и проверки конфликтов, а не условие базового Swarm.

### Ресурсы и стоимость эксплуатации

VibeForge — ориентир по RAM, CPU, размеру установки, росту данных и отзывчивости при сопоставимых сценариях. Больший расход заранее не согласован. Сравнивать одинаковые задачи, число участников, CLI/модели/настройки, холодные и прогретые запуски; указывать разброс и погрешность, не делать вывод по одной удачной цифре. Учитывать приложение, все CLI/helpers, зависимости, кеши, транскрипты, worktrees, фоновые процессы и состояние после Stop/закрытия окна, а не только `.app`.

Нужную функциональность не сокращать ради показателей. При устойчивом превышении сначала локализовать причину, предложить оптимизацию либо обоснованное изменение технологии; смена стека требует согласования. Не считать измерения пустой оболочки сравнением готовых продуктов, не обещать равенство без данных. До сопоставимых замеров статус — «не установлено»; неопределённость не означает разрешённый перерасход. Сбор базовых метрик начинается на первом рабочем сценарии и повторяется для Codex/Swarm, не откладывается целиком на упаковку.

6. В отчёте указывать изменённые файлы, команды и результаты, незакрытые критерии и следующий конкретный пункт. Изменение этой спецификации само по себе не считается исправлением реализации.
7. Перед созданием или изменением промптов обязательно изучить VibeForgeInfo и выполнить правила §12: переиспользовать готовые формулировки, обосновать адаптации и указать источники в отчёте. Это относится и к служебным инструкциям продолжения, исправления и доработки, а не только к шаблонам режимов.

За пределами первой полезной версии: командные стратегии сверх базового Swarm, облачная синхронизация, удалённые агенты, публичное распространение, автообновление CLI и работа с подмодулями/LFS. Их добавление требует отдельного решения и критериев; базовый Swarm и Claude/Codex уже обязательны.
