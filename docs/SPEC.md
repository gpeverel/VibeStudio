# Спецификация MVP: личный аналог VibeForge для macOS

Статус: черновик на одобрении. Кода нет. Пометка **[допущение]** значит, что это выбор исполнителя, который можно изменить.

## 0. Принятые решения

| Тема | Решение |
|---|---|
| Стек | Electron + TypeScript (strict) + React + Vite (electron-vite). Node 24, пакетный менеджер npm, чтобы не ставить лишнего **[допущение]** |
| Запуск агента | Подпроцесс `claude -p --output-format stream-json --verbose`, один процесс на ход, продолжение через `--resume <id>`. Без `--bare` (он не работает с подпиской) |
| Права по умолчанию | `acceptEdits` + разрешённые команды проекта + deny на опасное + `--permission-prompts none`. Отказы показываются в UI, кнопка «Разрешить и повторить» |
| Хранение | SQLite (`better-sqlite3`, SQL-миграции) в `~/Library/Application Support/<App>` + JSONL-журнал сырых строк потока |
| Git | Системный `git` через `execFile`, без обёрток. Worktree создаёт само приложение, а не флаг `--worktree` |
| Тесты | Vitest. Разбор потока проверяется на записанных настоящих образцах. Для git используются настоящие временные репозитории |
| Живая запись образцов | Два коротких запуска в этапе 0 на одноразовом репозитории в `.tmp/` внутри проекта. Первый с `--no-session-persistence`, второй с сохранением, чтобы проверить `--resume`. После второго показать `claude purge --dry-run` для этого пути и чистить транскрипты только с подтверждения пользователя |

Границы первой версии: только macOS; агент только Claude Code CLI (за интерфейсом-адаптером); ключи не вводятся, используется установленный и авторизованный `claude`; приложение ничего не отправляет наружу.

Отложено, но архитектуру не ломаем: режимы Swarm, Fusion, Orchestrator; дизайн-режим; skills; iPhone; запуск по ssh; голос; Windows; автоматический агент-ревьюер; режим «Проверка».

## 1. Спецификация MVP

**Сценарий.**
1. Добавляете git-репозиторий как проект.
2. Создаёте сессию: пишете задачу и выбираете режим задачи.
3. Приложение фиксирует точку возврата, создаёт worktree и ветку `vs/<id>-<слаг>`, выполняет команду подготовки.
4. Запускает Claude Code в этой worktree.
5. Вы видите ход работы: ответы, вызовы инструментов, правки.
6. По завершении запускаются проверки. При падении результат уходит агенту, до N попыток.
7. Вы смотрите дифф, оставляете замечания под строками, агент переделывает.
8. Commit, Push, «Применить» (merge в базовую ветку) или «Отбросить».

**Режимы задачи.** Шаблоны промпта (файлы `src/core/modes/*.md`) плюс профиль прав:

| Режим | Правки | Профиль |
|---|---|---|
| Агент, Поиск бага, Тесты | Да | `acceptEdits` + allowlist (для «Тесты» в нём команда тестов проекта) |
| План, Опрос, Вопрос, Ревью | Нет | `dontAsk` + `Read/Grep/Glob`; `Edit/Write/NotebookEdit` убраны из инструментов через `--disallowedTools` |

Без прав вопросы агент выводит текстом, а не интерактивно: `AskUserQuestion` при `--permission-prompts none` недоступен.

**Статусы сессии для пользователя.** Подготовка, Работает, Проверка, Исправление (попытка 2 из 3), Готово к ревью, Проверки не прошли, Нужно разрешение, Ошибка среды, Остановлено, Прервано (после падения), Применено, Отброшено.

**Нефункциональное.**
- Файлы пользователя читаются через git. Дифф строится из `git diff <base_sha>`.
- Приложение само ничего не отправляет наружу. Единственный сетевой вызов — `git push` по явному нажатию.
- Окно Electron: `contextIsolation`, без `nodeIntegration`, строгий CSP, типизированный IPC с проверкой через zod.
- В недоверенных репозиториях `-p` выполняет хуки из `.claude/settings.json` проекта. При добавлении проекта показывается предупреждение.

## 2. Архитектура

**Структура: один пакет, папки с границами, которые проверяет `dependency-cruiser`.**

```
src/
  shared/    типы, zod-схемы IPC и событий (без зависимостей)
  core/      домен и оркестрация, чистый TS: ничего из electron/fs/sqlite напрямую
  adapters/  claude (запуск и разбор), git, process-runner, store (SQLite), journal
  main/      Electron main: сборка зависимостей, IPC-обработчики, окна
  renderer/  React UI (знает только shared и window.api)
```

Правило: `core` зависит только от `shared` и собственных интерфейсов-портов, адаптеры реализуют порты. Поэтому ядро тестируется целиком с фейками.

**Порты ядра.** `AgentAdapter`, `GitPort`, `ProcessRunner`, `Store` (репозитории), `Journal`, `Clock`, `IdGen`.

```ts
interface AgentAdapter {
  kind: AgentKind;                       // 'claude-code' сейчас, позже 'codex' и т.д.
  capabilities: { resume: boolean; readOnly: boolean; partialText: boolean; usage: boolean };
  detect(): Promise<AgentEnvironment>;   // путь, версия, авторизация, понятная причина отказа
  start(req: AgentRunRequest): AgentRun;
}
interface AgentRunRequest {
  cwd: string; prompt: string; agentSessionId: string; resume: boolean;
  profile: PermissionProfile;            // mode + allow[] + deny[]
  model?: string; maxTurns?: number; env: Record<string,string>;
}
interface AgentRun {
  events: AsyncIterable<AgentEvent>;
  interrupt(): Promise<void>;
  kill(): void;
  done: Promise<AgentRunResult>;
}
```

**События агента (нормализованные, не привязаны к Claude).**
- `run_started` (модель, инструменты)
- `text` (дельта или сообщение)
- `tool_started` / `tool_finished` (имя, краткий ввод, успех, превью вывода)
- `permission_denied` (инструмент, ввод, подсказка правила)
- `retry` (причина, попытка)
- `usage` (токены)
- `rate_limit`
- `run_finished` (`status`: success, error, max_turns, interrupted, limit; токены; оценка стоимости; длительность; `errorKind`: not_logged_in, usage_limit, overloaded, network, unknown)

Сырые строки потока сохраняются в JSONL-журнале, поэтому любой сбой разбора можно воспроизвести. Состав правок берётся из git, а не из событий.

**Модель сессии под режимы команды (главная точка расширения).**
- `Session` (задача пользователя) имеет `teamMode` и состояние стратегии.
- `Participant` (роль, агент, модель, профиль, ссылка на `Workspace`, `agentSessionId`).
- `Workspace` (путь worktree, ветка, `base_sha`, порт). Отдельная сущность от сессии.
- `Turn` (один запуск агента: чей, вид, промпт, статус, токены).

Solo — один участник в одной рабочей области. Остальные режимы добавляются без переписывания ядра:
- **Swarm:** 3 участника в одном `Workspace`, первый ход договаривается о зонах.
- **Orchestrator:** N участников, у каждого свой `Workspace`, плюс таблица `work_items` отдельной миграцией.
- **Fusion:** несколько read-only участников, судья и исполнитель.

```ts
interface TeamStrategy {
  mode: TeamMode;
  start(ctx: SessionContext): Promise<NextAction>;
  onTurnFinished(ctx: SessionContext, turn: Turn): Promise<NextAction>;
}
type NextAction =
  | { kind: 'run_turn'; participantId: string; prompt: string }
  | { kind: 'run_checks' } | { kind: 'await_user' } | { kind: 'done' };
```

`SessionEngine` — детерминированный автомат: выполняет `NextAction`, пишет в Store и Journal, рассылает события. Его можно целиком тестировать с `FakeAgentAdapter`, который проигрывает записанные образцы.

**Модель данных (SQLite).**
- `projects(id, path, name, default_branch, config_json, ...)`
- `sessions(id, project_id, title, task_mode, team_mode, status, status_detail, base_ref, base_sha, branch, applied_sha, created/updated/finished_at)`
- `participants(id, session_id, role, agent_kind, model, workspace_id, agent_session_id, profile_json)`
- `workspaces(id, session_id, path, branch, base_sha, port, state)`
- `turns(id, session_id, participant_id, seq, kind, prompt, status, pid, started_at, ended_at, usage_json, error_kind)`
- `events(id, session_id, turn_id, participant_id, seq, ts, type, payload_json)`
- `check_runs(id, session_id, turn_id, attempt, name, command, status, exit_code, log_path, ...)`
- `review_comments(id, session_id, file, line, anchor_text, body, status)`
- `settings(key, value)`

Миграции — нумерованные SQL-файлы, версия в `PRAGMA user_version`.

**Конфигурация проекта** хранится в БД, редактируется в UI, в репозиторий ничего не пишется. Поля: базовая ветка, команда подготовки, файлы для копирования или симлинков, проверки (имя, команда, таймаут, обязательность), allowlist/denylist команд, макс. попыток исправления, способ применения (по умолчанию squash).

### Git-логика
- **Точка возврата.** Перед стартом пишется `refs/vibestudio/<id>/base`. Перед «Применить» пишется `…/pre-apply`, для отката применения.
- **Применение без конфликтов в вашей копии.** Сначала базовая ветка вливается в ветку сессии внутри worktree (конфликт там разбирает агент по кнопке «Разрешить конфликты»). Затем в вашу копию переносится результат squash-слиянием, которое конфликтовать уже не может. Ваша копия до этого момента не меняется.
- **Крайние случаи:**
  - Нет git — понятная ошибка и предложение `git init` с подтверждением. Нужен минимум один коммит.
  - Грязное дерево при старте — worktree строится от HEAD, предупреждение, что незакоммиченное агент не увидит.
  - Грязное дерево при «Применить» — блок с перечнем файлов.
  - Detached HEAD — сессия идёт от SHA, «Применить» заменяется на «Оставить ветку».
  - Базовая ветка удалена — выбрать другую цель или оставить ветку сессии.
  - Удалённая ветка пропала — `push` создаёт её заново, force-push не поддерживается.
  - Подмодули и LFS — не поддерживаются, предупреждение.

### Цикл проверок
После успешного хода обязательные проверки идут по очереди в worktree (каждая в своей группе процессов, с таймаутом и ограничением размера лога). При падении агент получает «хвост» вывода в промпте исправления, до N попыток. Если вывод падения повторился дважды подряд, цикл останавливается раньше. Итоговый статус — «Проверки не прошли» с логами. Можно отправить свою инструкцию или «Применить без проверок» с подтверждением.

### Разрешения
Отказ приходит как событие `permission_denied` и список `permission_denials` в `result`. UI показывает «Агенту отказано в: `<команда>`» и кнопку «Разрешить и повторить». Она добавляет правило в allowlist проекта (на сессию или навсегда) и запускает продолжение. Опасное блокируется deny-правилами: `rm`, `git push`, `curl`/`wget`, `sudo`, запись вне worktree и в основную копию.

### Замечания на строках
Замечание хранит файл, сторону, номер строки, текст строки (для повторной привязки) и тело. Все открытые замечания уходят агенту одним сообщением. После хода замечания, чья строка пропала, помечаются устаревшими.

### Параллельность
Лимит одновременных агентов (по умолчанию 3 **[допущение]**), остальные в очереди. У каждой сессии свой порт (`PORT`, `VIBESTUDIO_PORT_1…`), передаётся в команды подготовки, проверок и агенту. При запуске приложение сверяет `git worktree list` и БД. Сироты показываются на экране «Уборка» и сами не удаляются, если есть незакоммиченное или неопубликованное.

### Восстановление
Свой UUID `--session-id` записывается до запуска процесса. Вместе с ним пишутся pid и время старта. После падения сессии в состояниях «Работает/Проверка» получают статус «Прервано», старые процессы-сироты завершаются (после сверки командной строки), доступна кнопка «Продолжить» через `--resume`.

### Ошибки среды
До старта: `claude auth status` и версия (минимум 2.1.259 из-за `--permission-prompts`). Сообщения для not logged in, лимитов (с временем сброса из текста), перегрузки, сети и обрыва потока без `result`. Для обрыва — «Прервано, можно продолжить».

### Расход
Токены (вход, выход, cache) и время по сессии из `result`/`modelUsage`. Доллары показываются только как «оценка» в подсказке.

## 3. План этапов

Принцип: каждый этап заканчивается работающим приложением. Работа внутри этапа идёт задачами не больше одного логического шага, сначала тест, потом код. В репозитории будет `CLAUDE.md` с правилами для вайбкодинга: границы слоёв, команды `npm test`, `npm run typecheck`, `npm run lint`, «ничего вне проекта».

**Этап 0. Основа и разведка.**
- Каркас electron-vite, TS strict, ESLint, Vitest, `dependency-cruiser`, минимальные дизайн-токены (один файл).
- Экран «Диагностика»: путь к `claude`, версия, `auth status`.
- Запись образцов потока по плану выше и парсер на них.
- *Приёмка:* `npm test`/`typecheck`/`lint` зелёные, приложение запускается, показывает все три состояния (всё хорошо, нет входа, нет бинарника), образцы закоммичены, парсер превращает их в нормализованные события.

**Этап 1. Ходячий скелет.**
- Добавление проекта, создание сессии Solo/«Агент», worktree + ветка, запуск Claude, живая лента событий, «Остановить», SQLite и журнал.
- *Приёмка:* на тестовом репозитории задача выполняется, лента идёт в реальном времени, после перезапуска сессия видна. Автотест: HEAD и `git status` основной копии не изменились.

**Этап 2. Изменения и применение.**
- Дифф по файлам, Commit, Push, Применить (squash), Отбросить, точки возврата, все крайние случаи git, конфликты через ветку сессии.
- *Приёмка:* тесты на временных репозиториях для каждого случая; отказ при грязном дереве; откат применения.

**Этап 3. Копия проекта и проверки.**
- Команда подготовки, копирование и симлинки файлов, проверки с логом и таймаутами, цикл исправления с лимитом.
- *Приёмка:* падающая проверка возвращается агенту, после N попыток статус «Проверки не прошли»; `.env` и `node_modules` доступны в worktree.

**Этап 4. Замечания на строках.**
- Комментарии под строкой, отправка пачкой, переделка, пометка устаревших.
- *Приёмка:* замечание доходит до агента, новый ход меняет дифф, устаревшие замечания видны.

**Этап 5. Режимы задачи и разрешения.**
- Все семь шаблонов с профилями прав, экран отказов, «Разрешить и повторить», настройка allow/deny.
- *Приёмка:* в режиме «План» ни один файл не меняется (тест на worktree); отказ превращается в правило и ход повторяется.

**Этап 6. Параллельность и уборка.**
- Очередь и лимит, порты, экран «Уборка», сверка при запуске.
- *Приёмка:* три сессии одновременно без конфликта портов; забытая worktree находится и удаляется только после подтверждения.

**Этап 7. Устойчивость, расход, упаковка.**
- Все ошибки среды с понятными текстами, восстановление после падения, показ токенов и времени, сборка `.app` для локального запуска (без подписи).
- *Приёмка:* принудительное завершение приложения посреди хода → после запуска «Прервано» и рабочее «Продолжить»; неавторизованный `claude` даёт понятное сообщение.

## 4. Риски
- Форматы событий и флаги зависят от версии CLI: вся привязка в одном адаптере, проверка минимальной версии, живые тесты за флагом `LIVE=1` (не в обычном прогоне).
- `better-sqlite3` надо пересобирать под Electron: решается на этапе 0 и проверяется сразу.
- Выбор библиотеки диффа: рассматривается `react-diff-view` из-за встроенных виджетов под строкой **[допущение]**, проверить перед этапом 2.
- Условия использования подписки: в обзоре Agent SDK сказано, что сторонним разработчикам без одобрения нельзя предлагать вход через claude.ai или лимиты подписки в своих продуктах. Приложение личное, вход и токены не трогает, запускает установленный `claude` подпроцессом и не распространяется. Название продукта не должно содержать «Claude Code».
- Без `--bare` запуск `-p` подхватывает хуки и MCP из репозитория без запроса доверия: для чужих репозиториев нужно предупреждение.
