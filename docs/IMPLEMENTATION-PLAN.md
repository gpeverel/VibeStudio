# План реализации после принятия продуктовых решений

Дата: 2026-10-11. Нормативные требования — [SPEC.md](SPEC.md), решения пользователя — [ARCHITECTURE-REASSESSMENT.md, §0](ARCHITECTURE-REASSESSMENT.md), доказательства и исторический статус — [STAGE-0C-REPORT.md](STAGE-0C-REPORT.md).

**План не разрешает автоматически начинать следующие пакеты.** По отдельному поручению пользователя реализован контрактный срез P1; матрица doubles проходит, результаты проверок и оставшиеся ограничения приведены в заключительном разделе [STAGE-0C-REPORT.md](STAGE-0C-REPORT.md). Smoke в текущей среде завершился SIGABRT и не считается пройденным. Старый строгий 0C не пройден; реальная практическая совместимость, Codex и Swarm ещё не реализованы. Номера P1–P8 ниже обозначают пакеты, не приоритеты SPEC.

## 1. Результат и границы

Первая полезная версия: локальная `.app` для macOS с Claude Code и Codex, штатной авторизацией, worktree, Solo и базовым Swarm, понятными режимами/правами/Stop, управляемыми проверками и Git, восстановлением и измеренной стоимостью ресурсов. Solo допускается первым внутренним срезом, но не принимается за всю целевую версию.

Сохраняем parser, builder, ProcessRunner, Git и Electron-каркас. Не строим универсальную платформу провайдеров, плагинов или стратегий. VM, обязательные контейнеры, guest-login, привилегированные службы, переподпись CLI, перенос токенов и молчаливое обновление CLI не входят в план. Лаборатории `tests/isolation/**` и реальные fixtures сохраняются; они не обязательный runtime backend.

Новые живые вызовы, в том числе auth-проверки с возможными служебными записями, не следуют из одобрения плана: нужен отдельный согласованный сценарий. Ни в P1, ни при подготовке документа не запускать настоящие CLI, старый live-runner или N1–N3, не устанавливать ПО.

## 3. P1 — небольшой первый пакет доступа и запуска

### Цель и наблюдаемое поведение

Привести типы и маршрутизацию допуска в соответствие с принятым практическим профилем, сохранив смысл и защиту старого строгого контракта. Не включать реальные пользовательские запуски до проверки практических предпосылок. На тестовом CLI должно быть доказано, что явно выбранный практический профиль запускается через свой допуск, а старый строгий запрос без verifier — по-прежнему нет.

Ожидаемые изменения данных (имена новых типов окончательно согласует владелец A до правок потребителей):

1. Существующий `AccessProfile` сохранить как legacy strict, чтобы старые helpers/fixtures не стали практическими неявно. Добавить рядом узкий `PracticalLocalReadProfile` с явным `kind: 'practical-local-v1'`, `mode: 'read-only'`, закрытыми инструментами, allow/deny и явной политикой проектных расширений. `AgentRunRequest.profile` принимает различимые варианты. Отсутствие нового kind означает прежний строгий вариант, а неизвестный kind — отказ, не fallback.
2. Практический профиль описывает ожидаемые операции в workspace и доверие проекту, но не объявляет `readRoots/writeRoots/network` обеспеченными средствами ОС. Не добавлять Bash/Edit/Write, новые env-переменные, bypass permissions или проектные hooks/MCP/plugins ради нового маршрута. Builtin совместимость — предмет P2b, а не фиктивное `loadPlugins:false` обо всём процессе.
3. `detect.status` означает готовность самой CLI (binary/interface/auth), отдельно от допуска конкретного профиля. Наличие флагов остаётся объявленной возможностью; старое `capabilities.readOnly` не получает verified. Можно сохранить его как legacy-поле с явным описанием, не устраивая миграцию всех capabilities в P1.
4. В доверенной композиции адаптера добавить узкую оценку практического допуска для конкретного запроса/CLI/argv/env. Результат различает ready, blocked и unsupported, содержит типизированные причины/ограничения; **не является AccessVerification и не возвращает verified/evidence/изоляционный launch**. Отсутствие оценки или обязательных данных даёт явную ошибку недопуска практического профиля до prompt. Строки renderer или модели не могут выдать ready.
5. Старый маршрут использует только launch строгого AccessVerifier. Новый маршрут при разрешающей оценке использует существующий ProcessRunner напрямую, не изображая его песочницей. Оценивается и запускается один и тот же неизменённый набор аргументов/окружения/профиля; ошибка или stop во время оценки не допускает поздний запуск.

**Граница P1:** production-оценка реальной совместимости ещё не выдаёт ready. Положительная подстановка существует только в тестах и явно названа synthetic. В приложении нет UI выбора/подключения такого допуска. Это законченный контрактный шаг с работающим тестовым маршрутом, а не обещание уже запускаемого продукта. P2b заменяет отсутствие практической оценки конкретной проверкой предпосылок CLI; он не возвращает требования доказать абсолютную ОС-изоляцию.

### Матрица перехода

| Вход | Допуск | Ожидаемый результат |
|---|---|---|
| Старый профиль, новый kind отсутствует | Нет строгого verifier | `profile_unverified`, prompt не запущен |
| Старый строгий профиль | verified/evidence без связанного launch | Прежний отказ, обычный runner не используется |
| Старый строгий профиль | Доверенный verifier со связанным launch | Существующая семантика; production-реализация не добавляется P1 |
| Явный practical-local-v1 | Нет практической оценки, blocked, неизвестная обязательная предпосылка | Типизированный недопуск с причиной, prompt не запущен; не подменять его старым успехом |
| Явный practical-local-v1 | Unsupported или конфликт конфигурации | Понятный отказ без расширения tools/env/settings и без попытки другой политики |
| Явный practical-local-v1 | Ready от synthetic-оценки в тесте | Прямой runner с тем же проверенным запросом; нет AccessVerification/verified |
| Любой | Неверный запрос, отсутствующая CLI/auth, нужная возможность отсутствует | Прежние самостоятельные причины отказа, не маскируемые выбором профиля |
| Любой | Неизвестный kind, stop/error во время допуска | Отказ/прерывание без позднего prompt; единственный согласованный terminal result |

### Разрешённая область будущих изменений P1 и владение Swarm

| Владелец | Эксклюзивные файлы | Обязанность |
|---|---|---|
| A — контракты и политика | `src/core/ports/agent.ts`, `src/shared/agent.ts`, `src/adapters/claude/profile.ts` | Типы вариантов и допуска, причины ошибок, валидаторы. Сначала публикует контракт, после замечаний фиксирует его до интеграции |
| B — маршрутизация адаптера | `src/adapters/claude/index.ts`, `args.ts`, `detect.ts` | Встраивает утверждённые типы, сохраняет argv/env ограничения и строгий launch, новый практический маршрут; не редактирует общие типы |
| C — независимые проверки и отчёт | `tests/claude/access-profile.test.ts`, `detect.test.ts`, `adapter-lifecycle.test.ts`, новый `tests/claude/practical-profile.test.ts`, `tests/helpers/claude/requests.ts`; `docs/STAGE-0C-REPORT.md`, `docs/IMPLEMENTATION-PLAN.md` | Матрица отказов/успеха, явные legacy/practical helpers, перекрёстная проверка и фактический отчёт. Shared helper имеет одного владельца |

Любой новый файл в этих областях сначала объявляется команде. Остальные файлы в P1 не менять: parser и инструкции модели, ProcessRunner/его порт, Git, main/preload/UI, SQLite, Codex, Swarm, live-runner, fixtures, лаборатории, SPEC, зависимости/конфигурация. Если нужное изменение выходит за границу, зафиксировать причину и предложить отдельный пакет, не расширять задачу незаметно.

Фаза координации — только чтение и сообщения: каждый объявляет область, контракты и риск. A публикует варианты типов и ошибки; B проверяет пригодность для adapter, C — независимые ожидания. Затем A фиксирует контракт. B и C могут работать параллельно только в своих файлах; перед правкой перечитывают их. Во время ожидания общего контракта C изучает регрессии, B — цепочку запуска, не создают собственные конкурирующие типы. Один владелец каждой строки, обсуждение по существу без подтверждающего шума. Перед передачей B проверяет валидацию A, C проверяет отсутствие обходов B, A проверяет полноту тестовой матрицы. Неснятое разногласие записывается, не маскируется общим «согласовано».

### Критерии приёмки P1

- На fake CLI проходят обе ветви матрицы; старый профиль без kind остаётся строгим. Положительный практический тест не вызывает строгий verifier, строгий тест не вызывает обычный runner в обход проверенного launch.
- Invalid/unknown kind, нет доверия/готовности, несовместимая CLI/auth, config conflict, расширение tools, запрещённый env и отмена до launch не создают prompt-процесс. Простая диагностика binary/help/auth double не считается модельным launch.
- Новый практический argv не получает более широких tools/allow/permissions и автоматически включённых источников конфигурации. Отдельно проверяются точность stdin/session-id/resume и сохранение результата/ошибок без дублирования terminal event.
- `detect.status=available` для исправного double не означает `readOnly=verified` и не разрешает start. В старом `detect.test.ts` ожидание `unavailable` исключительно из-за profile_unverified явно обновляется на новую семантику диагностики; рядом сохраняются проверки unverified и фактического запрета строгого start. Это документированное изменение контракта, не удаление проверки защиты.
- Строгие тесты отказа без evidence/launch, ограничения argv/env, parser/setsid и реальные replay сохранены. Допустима механическая адаптация типов с теми же поведенческими assertions; запрещены skip, удаление отрицательных случаев и замена реальных fixtures синтетическими.
- Нет постоянного ready-callback, флага от renderer или config, выдающего фиктивный допуск. Новые типы, legacy-совместимость и незакрытая реальная готовность описаны в отчёте; 0C не закрыт.

### Проверки P1

Один участник C выполняет итоговый прогон после сведения изменений, без параллельных одинаковых наборов. С установленной средой через `sh scripts/with-node.sh` выполнить целевые Vitest-файлы, затем требуемые `npm run typecheck`, `npm run lint`, `npm run check:boundaries`, `npm test`, `npm run test:node`, `npm run build`, `npm run smoke`; `git diff --check` и контроль области изменений. Целевой Vitest запускается существующим npm exec с запретом скачивания, без установки пакетов. Конкретные exit codes/числа записать как получены, а не заранее 262/262. Падение GUI/отсутствующие зависимости фиксировать; не устанавливать ПО и не ослаблять проверки. Реальная CLI, `test:live`, OS-лаборатории и пользовательские проекты не запускаются. Полный набор не повторять без новой правки/ошибки.

## 4. Последующие пакеты

### P2a — различимый Stop и lifecycle

Цель: исход задачи не скрывает ошибки завершения, а UI/engine может безопасно решать, когда разрешать следующий ход. Файлы: `src/core/ports/process-runner.ts`, `src/shared/agent.ts`, `src/core/ports/agent.ts` при необходимости, `src/adapters/process-runner/index.ts`, `src/adapters/claude/index.ts`, process/lifecycle tests. Отдельные поля/тип для подтверждения exit, результата сигналов, drain/timeout/errors и непроверяемого отсутствия detached-потомков; API не обещает нового OS-механизма.

Приёмка: обычный ребёнок остановлен в тесте; SIGTERM-ignore эскалируется; signal failure, drain timeout, stop до spawn, поздний result и повтор Stop не теряют ошибки и не дают success. Существующий detached-marker остаётся отрицательным доказательством полного stop. На doubles покрыть неподтверждённый exit; на собственных временных процессах — обычную группу. После deadline done конечен, но cleanup не выдаётся за успешный. Не убивать сторонние процессы. В P5 проверить блокировку последующих записей при такой ошибке.

### P2b — практический Claude и его приёмка

Цель: production-оценка P1 выдаёт ready только при конкретной совместимой CLI/auth/конфигурации, сохраняя штатные helpers. Файлы: `src/adapters/claude/{detect,profile,args,index,parser}.ts`, безопасный inventory в `src/shared/agent.ts`, `tests/claude/**`, отдельный новый практический live-стенд и новые reviewed fixtures. Новый live-стенд отделить от старого строгого; старые ожидания не переписать ради успеха. При необходимости оформить новое описание сценария, исторические планы не считать действующим разрешением.

Подзадачи: разделить проектные источники, builtin и managed; определить необходимые доступные предзапусковые проверки и причины неизвестности; сопоставить runtime inventory с ожидаемым без секретов; ошибка после init останавливает дальнейший ход, но не доказывает, что ранний hook не исполнился. Ready привязан к конкретной CLI/версии/конфигурации и контексту, не к слову «доверенный». Никакой новой ОС-песочницы или собственного механизма выдачи credentials.

Приёмка на doubles: неизвестное не становится пустым/готовым, конфликты блокируют, штатная auth не подменяется env-токеном, права не расширяются. Live отдельно согласуется: конечные точечные пробы реального read/tools, штатного auth, persistence/resume и отличимой смены инструкции, контроля расширений и Stop на собственном стенде. Существующие 01–03 учитывать, повторять только если нужна новая комбинация. Не обходить safeguards и не повторять 04. Provider refresh, который не удалось наблюдать, остаётся неизвестным с описанием обработки отказа; не изобретать успешную проверку. Результат — приёмка конкретного practical-профиля Claude, не всего 0C/продукта.

### P3 — установленный Codex CLI

Цель: второй адаптер с теми же продуктовыми правами и честными пределами, штатным входом и сохранением диалога. Файлы: новый `src/adapters/codex/**`, будущие `tests/codex/**`, отдельные fixtures/live-сценарий; общие порты/DTO — только через одного назначенного владельца. Не переносить Claude UUID, argv, событийные поля и auth-команды по аналогии.

Порядок: изучить текущую официальную документацию и доступные материалы установленной CLI; составить карту команд, auth, протокола, approvals/config и ID; сначала doubles/parser, затем отдельно разрешённые реальные пробы. Если требуемую политику конкретная CLI не поддерживает, capability остаётся unavailable с причиной, не включается bypass. Приёмка: обнаружение, штатная auth, first turn/resume, инструменты/отказы, ограничения вывода, Stop, отсутствие скрытых project extensions и секретов в диагностике. Смешанный Swarm не выдаёт историю одной CLI другой как resume.

### P4 — согласие на команды проекта

Цель: повтор согласованной проверки удобен, изменение исполняемого содержимого требует нового решения. Файлы: будущая чистая политика согласия в `src/core/`, DTO в `src/shared/`, tests; затем Store/IPC/UI в P5. Согласие включает проект, назначение, команду/аргументы/cwd, существенные права и идентичность известных исполняемых scripts/входов. Нужен проверяемый fingerprint, а не один hash строки `npm test`; граница покрытия зависимостей описывается, не обещается доказательство всего исполняемого кода.

Приёмка: неизменный повтор без вопроса; изменение тела script при прежнем имени, вызываемого известного script, команды, прав, cwd/назначения инвалидирует согласие; чтение/проверка перед запуском, недоступный/неоднозначный вход — отказ с объяснением. Push/публикация/разрушение отдельно. Адаптер не получает общий Bash-bypass; если CLI не поддерживает достаточное ограничение, проверка остаётся именованной операцией приложения. Тесты на временных файлах, без настоящей CLI. После подключения Store — сохранение и отзыв согласия при перезапуске.

### P5 — durable Solo и восстановление

Цель: первый внутренний end-to-end срез с реальным состоянием приложения. Файлы: будущие engine/SoloStrategy, store/migrations/journal/workspace-files, `src/shared/app-api.ts`, main/preload/renderer и интеграционные тесты. Не переписывать Git 0B; отдельно завершить G9/G10 из его отчёта до небезопасных операций, связать существующий GitOperationStore с durable хранением.

### P7 — базовый Swarm в первой полезной версии

Цель: несколько Claude/Codex участников, согласованное владение, сообщения и общий результат. Файлы: будущая SwarmStrategy/простая очередь, DTO сообщений/решений/владения, миграции/events, командный renderer и tests. Переиспользовать участника/ход/adapter; не вводить универсальный plugin engine.

Инженерная первая модель: общая worktree, параллельные исследовательские ходы, сериализованные изменяющие ходы; setup/check/apply не пересекаются с записями агентов. Владение подтверждается участниками, спор виден; инструкции не объявляются файловыми блокировками. Общий результат содержит источники вкладов и существенные разногласия.

Приёмка: сценарий трёх участников, включая обе CLI; фазы координации и работы, сообщения/решения, restart без двойной доставки/ходов, ограниченные раунды, отсутствие коллизий писателей. ### P8 — интерфейс, ресурсы, установка и восстановление

Цель: удобство локального приложения без необоснованного перерасхода. Прежде расширения UI команда документирует основания сохранения Electron и проверяемые альтернативы без смены стека; чужие бенчмарки или размер одной `.app` не заменяют измерение.

Сценарии: idle, холодный/прогретый старт, первый ход, resume, Stop, три участника, закрытие окна, рост данных после нескольких сессий. Одинаковые CLI/версии/модели/задачи/настройки; повторения с разбросом. RAM всех связанных процессов (метрика названа, суммарный RSS не выдавать за точную уникальную память), CPU-time, время до события/реакции UI, размер установки/зависимостей/кешей/transcripts/worktrees, фоновые процессы и очистка только собственных данных. Устойчивое превышение VibeForge не принято заранее: локализовать причину, предложить оптимизацию либо согласуемую смену технологии. Упаковка не навязывает гостевой runtime/службы/повторный login; установка и восстановление пользовательского состояния проверены отдельно. Секреты и чужие беседы в измерения не попадают.

## 5. Владение в последующих Swarm-пакетах

Перед каждым пакетом заново закрепить точные пути: A — общие порты/DTO и чистая доменная политика; B — соответствующий адаптер/интеграция; C — независимые tests/evidence/отчёт. Миграции, общий helper, SessionEngine и renderer-файл всегда имеют ровно одного владельца; если A владеет engine, B его не правит «для интеграции», а отправляет необходимое изменение. Для P2a общие process/agent результаты согласуются до правок runner. Для P3 owner нового Codex не меняет Claude. Для P5/P7 владелец миграций сначала публикует данные/инварианты, остальные строят потребителей после фиксации контракта.

Это разделение обязанностей, не требование параллелить зависимые шаги. Общие проверки выполняются один раз после интеграции; сложное изменение может иметь меньший состав команды. Источники реальных записей, ограничения и разногласия сохраняются в итоговом отчёте.
