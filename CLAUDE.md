## Окружение

- Node 24 для разработки (`engines`, `.nvmrc`; Node 26 отклоняется `engine-strict`); npm, не pnpm/yarn.
- Для запуска без профиля оболочки использовать `sh scripts/with-node.sh npm …`: скрипт выбирает установленную версию из `.nvmrc` через PATH или NVM_DIR (по умолчанию `~/.nvm`). Подготовка и запуск workspace VibeForge заданы в `.vibeforge/workspace.json`. Сам `.nvmrc` не переключает Node для обычного `npm install`. Не отключать `engine-strict` для обхода EBADENGINE.
- Добавление `setup` не перезапускает подготовку уже созданной сессии. Если проверка перед передачей результата падает на автоматическом `npm install`, выполнить `sh scripts/with-node.sh npm ci --no-audit --no-fund` в текущей рабочей копии и дождаться успешной установки. При полном локальном кеше можно добавить `--offline`; не считать настройку setup или неудачную установку восстановлением окружения. Затем проверить линтер и тесты, которые запускает автоматическая проверка.
- В `.npmrc` задано `include=dev`; если в окружении `NODE_ENV=production`, на всякий случай ставить с `unset NODE_ENV`.
- npm 12 блокирует install-скрипты без `allowScripts` (список в `package.json`). Бинарник Electron скачивает корневой `postinstall` (кеш `.cache/electron`); `better-sqlite3` работает на prebuilds без install-скрипта. Установка: `npm ci`.
- Electron + TypeScript strict + React + electron-vite; SQLite через `better-sqlite3`.
- Версии Electron и нативных модулей закреплены; ABI better-sqlite3 для Electron отличается от Node — проверять оба.

## Команды

| Команда | Назначение |
|---|---|
| `npm test` | Vitest, только `tests/**/*.test.ts` |
| `npm run test:node` | Исходный Node-runner Git-границ (`node --test tests/run-git-boundaries.node.ts`) |
| `npm run test:e2e -- --repeat-each=3` | Одна сборка через `pretest:e2e`, затем три последовательных запуска сценария Playwright в Electron |
| `npm run typecheck` | TypeScript strict без вывода |
| `npm run lint` | ESLint |
| `npm run build` | Сборка electron-vite в `out/` |
| `npm run check:boundaries` | dependency-cruiser, правила в `.dependency-cruiser.cjs` |
| `npm run check:sqlite` | Проба better-sqlite3 под Node (`scripts/check-sqlite.mjs`) |
| `npm run check:sqlite:electron` | Та же проба под ABI Electron |
| `npm run rebuild:native` | Пересборка нативных модулей под Electron |
| `npm run smoke` | Запуск собранного Electron с `--smoke-test`: скрытое окно, проверка HTML и preload, выход за 15 с. Без Claude и пользовательских проектов |

Перед завершением задачи с изменениями кода прогнать `typecheck`, `lint`, `check:boundaries`, `test`, `test:node`, `test:e2e`, `smoke`. `test:e2e` сам выполняет `build` один раз перед прогоном; повторная отдельная сборка не нужна. Результаты записывать как есть; ограничение окружения фиксировать, а не объявлять успех. Для отдельной задачи только с документацией достаточно проверить diff и ссылки; это исключение не заменяет приёмку реализованного этапа.

`npm test` и `npm run test:node` используют `scripts/with-test-awake.sh`: на macOS `caffeinate -i` предотвращает автоматический сон только на время команды. Глобальные настройки питания и сон экрана не меняются; принудительный сон/закрытие крышки этим не предотвращаются. На других POSIX-системах команда запускается напрямую. Аргументы, код выхода и сигналы сохраняются; лимиты тестов не увеличиваются.

В `vitest.config.ts` задано `maxWorkers: 2`: тесты сами запускают Node/Git/Electron, поэтому параллелизм по числу ядер создаёт конкуренцию за ресурсы и может исчерпать deadline запуска дочерней команды. Нагрузочная проверка воспроизвела такой `SIGKILL` в `tests/test-command.test.ts` при восьми параллельных запусках. Обычный `npm test` выполняет весь набор с этим ограничением; таймауты, assertions и обработка ошибок сохраняются.

## Архитектура

```text
src/shared/    DTO, типы и zod-схемы; без Node/Electron и бизнес-логики
src/core/      домен, порты, SessionEngine; зависит только от shared
src/adapters/  claude, git, process-runner, workspace-files, store, journal
src/main/      сборка зависимостей, IPC, окна
src/preload/   мост к window.api
src/renderer/  React; приложение только через window.api
```

Границы проверяет `npm run check:boundaries`. Не ослаблять правила ради прохождения: исправлять импорт.

## Границы записи

- Тесты создают только собственные временные репозитории и каталоги и удаляют их.
- Не писать в пользовательские проекты, их основную копию и каталоги вне worktree/временной папки.
- Реальный Claude не запускать без явного разрешения и только в одноразовом репозитории (`LIVE=1`, не в обычном CI).
- Git — системный `git` через `execFile` с массивом аргументов, без shell.

## Полномочия исполнителя в VibeForge

Эти правила относятся к внешнему агенту, который работает над репозиторием, и применяются при передаче следующих этапов.

- Различай технические полномочия сессии и разрешённый пользователем объём работы. По ответу поддержки VibeForge от 2026-10-19 обычный Claude Code-агент использует `bypassPermissions`: это более широкие полномочия на всю его сессию, не разовое разрешение одной команды. Эффективные ограничения конкретного исполнителя определяются его текущей средой; сведения поддержки не заменяют их проверку.
- Согласие пользователя может охватывать команду, набор проверок или работу в сессии. Сохраняй его точный объём: не сужай до отдельного подтверждения каждой команды и не расширяй до несогласованных действий. При передаче работы указывай исполнителя, worktree, согласованный сценарий, существенные условия, бюджет и уже выполненные попытки. Не спрашивай повторно о том же неизменном и ещё не исчерпанном разрешении; новое решение нужно при выходе за его пределы. Например, разрешение P2b «один набор» уже израсходовано и не разрешает повтор.
- При `approval_policy=never` или недоступном механизме разовых подтверждений не предлагай подтвердить отдельную команду через этот механизм. Если нужен другой исполнитель, передавай подготовленный сценарий через штатное назначение пользователя; заранее поясняй, что выбор Claude меняет контекст и полномочия всей сессии. Уже согласованное назначение не требует повторного вопроса. Не запускай другой движок для обхода запрета текущей среды и не выдавай GPT-подагента за Claude Code.
- Более широкие права не разрешают менять HOME, авторизацию, глобальные настройки, hooks, sandbox или границы рабочей копии ради успешного запуска. При действующем запрете фиксируй отказ, прекращай заблокированный запуск и продолжай доступную независимую работу. Наличие hook не доказывает ОС-изоляцию дочерних процессов.
- Флаги и права внешнего Claude-агента не переносятся в проверяемый адаптер VibeStudio. Его инструменты, argv/env и ограничения определяются отдельным продуктовым контрактом; текущий practical read-only сохраняет Read/Glob/Grep.

Источник и подробная методика: [передача исполнителю P2b](docs/STAGE-0C-PRACTICAL-LIVE-PLAN.md#передача-исполнителю-после-ответа-поддержки-2026-10-19). Исторические ожидания разрешения в этом документе читать с учётом результата в его начале и последующих решений пользователя.

## Тесты и качество

- Не скрывать ошибки через `skip`, `todo`, ослабление assertions или расширение игнор-списков линтера.
- Существующий Node-runner и общий набор `tests/cases` сохраняются; Vitest запускает набор через `tests/spec-boundaries.test.ts` и не подхватывает `*.node.ts`.
- Типы известных результатов и коды ошибок — в производственном коде, без `Promise<unknown>` и свободных строк.

### E2E при работе по этапам

- Начиная с P6, при планировании каждого этапа и отдельно сдаваемого подэтапа заранее определить затрагиваемые пользовательские сценарии, ожидаемый результат и нужные тестовые данные. Новые или изменённые сценарии интерфейса покрывать Playwright-тестами в том же этапе, как только доступен полный путь через приложение; не откладывать их до P8. Для внутренних изменений без нового UI-сценария добавить подходящие модульные/интеграционные проверки и сохранить прогон существующих e2e.
- Перед закрытием каждого этапа или отдельно сдаваемого подэтапа после интеграции изменений выполнить полный локальный набор: `sh scripts/with-node.sh npm run test:e2e`. Обычный `npm test` его не запускает. После изменения e2e-сценариев или фикстур проверить устойчивость полного набора командой `sh scripts/with-node.sh npm run test:e2e -- --repeat-each=3` — этот прогон засчитывается и как полный.
- В отчёте этапа указать проверенные сценарии, фактическую команду, результат и подтверждение очистки из вложений `cleanup`. При падении или невозможности запуска этап не считать полностью проверенным: зафиксировать конкретную причину и оставшуюся проверку. Не отключать тесты и не ослаблять assertions ради закрытия этапа.
- Переиспользовать изоляцию ниже; штатные e2e не должны обращаться к реальным моделям, CLI Claude/Codex или пользовательским проектам. Для новых сценариев предусмотреть детерминированные подмены внешних зависимостей. Успех текущего теста выбора проекта не подтверждает новые функции P6; живая приёмка CLI Claude/Codex остаётся отдельной проверкой с отдельным разрешением.

### E2E: первый этап

- Локальный запуск: `sh scripts/with-node.sh npm run test:e2e` (для проверки устойчивости добавить `-- --repeat-each=3`). Нужны графическая сессия macOS и рабочий Electron/SQLite; браузеры Playwright отдельно скачивать не требуется. `pretest:e2e` собирает приложение один раз на весь прогон, не на каждый повтор.
- Конфигурация — `playwright.config.ts`, фикстура — `tests/e2e/fixtures.ts`, тестовый вход — `tests/e2e/electron-main.mjs`. Вход задаёт отдельные `userData`, `sessionData` и каталог логов до загрузки настоящего `out/main/index.js`. SQLite создаёт производственный код. Тест использует собственный Git-проект без remote; HOME и авторизация CLI не меняются, модели и реальные CLI не запускаются.
- Каждый тест создаёт `.tmp/vibestudio-e2e-*`. После подтверждённого завершения Electron удаляется весь каталог: профиль, SQLite, журналы и репозиторий. Результат удаления и завершения процесса записывается во вложение `cleanup` отчёта. Неподтверждённое завершение или ошибка очистки роняют тест.
- Ошибки страницы, preload, основного процесса и renderer считаются провалом; ожидаемых ошибок в первом сценарии нет. Не добавлять общий список подавления ошибок. `retries: 0`, `failOnFlakyTests: true`; ожидания по состоянию интерфейса, без фиксированных пауз. Отчёты: `playwright-report/`, результаты: `test-results/` (не коммитить).
- Эталонных снимков и axe-проверок на первом этапе нет. Будущие снимки снимать и сравнивать только локально на этой macOS-машине; обновлять намеренно, с объяснением в сообщении коммита. Облачный CI, `scripts/check.sh` и pre-push пока не подключены; полный локальный набор перед каждым push — решение для следующего этапа, пересмотр при длительности свыше 5–10 минут.
